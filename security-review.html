Security review: Originals Protocol, VH-based Editor’s Draft 0.1

Target: SPEC.md, single-signature design (branch single-signature, uncommitted, 12 Oct 2026) · Review date: 12 Oct 2026 · Design review only. Upstream claims were checked against VH Log at f2f9fda and the did:vh pre-draft; no implementation exists.

Verdict. The single-signature design removes the two-proof problems of the earlier draft and suits a local vertical slice. It is not ready for hosted publication or an interoperable release. Moving prerotation to the DID side leaves the key that signs asset entries unprotected. A stolen key can deactivate, freeze or lock every Original it controls, and the rotation procedure contradicts the spec’s own rejection test. The author binding also needs pinning: which fields are signed, how keys are compared, and which verification methods count.

Detailed findings

High

F-01 · Rotation propagation contradicts the old-key test

§5 rotation (171–175), P5.3, §3, §12 test “old author key after DID rotation”
Issue
§5 says each asset log is moved to the new key by an entry signed with the old key. Without prerotation that is the only path: VH treats the prior entry’s updateKeys as active. If the author removes the old key from the DID first, that propagation entry is exactly what the §12 test says to reject, and the Original is frozen forever. If it is accepted, a thief’s entry signed with the old key looks identical: it can name an earlier DID version and backdate versionTime to one second after its predecessor.
Failure scenario
Alice suspects K1 is stolen and removes it from her DID straight away. Her 40 Originals still list K1. Under a strict reading all 40 are frozen; under a lenient one the thief can edit or fork any of them first.
Recommendation
  • Add a normative rotation order: add the new key to the DID, append an entry signed by the old key to each asset log that sets the new key while both are valid in the referenced DID version, and only then remove the old key.
  • Classify an entry whose key is absent from the latest author DID as “historically authorized, ordering unproven”. Do not call it invalid on that basis alone, and never report it as currently authorized.
  • Say plainly that Originals not yet moved to the new key cannot be recovered after a compromise without witnesses.
High

F-02 · A stolen author key can destroy or hijack every Original it controls

Key policy (161–163), §5 rotation, P6.5, P2.2, P5.3, §11 stolen-key row
Issue
Prerotation on the DID side protects only the DID log’s own update keys. The key that signs asset entries is a verification method, which DID prerotation does not cover, and asset logs have no prerotation of their own. Nothing constrains the updateKeys an entry sets; P2.2 and P5.3 check only the signing key.
Failure scenario
With K1 a thief can deactivate (terminal under VH and P6.5), freeze (updateKeys: []), or lock the Original by setting updateKeys to a raw key in no DID. Originals then rejects every later entry, and Alice’s K1 is no longer active, so the log is stuck for everyone. All three pass Originals rules today if they name a DID version that lists K1.
Recommendation
  • Add a rule that every key in an entry’s updateKeys MUST be an assertionMethod key of the author DID at the DID version named in that entry, with exactly one key except in a rotation entry.
  • Report freezing as its own lifecycle status.
  • For hosted Originals, require witnesses that check the signing key against the latest author DID state.
  • Either adopt prerotation on asset logs, or record as an explicit decision that one compromise can destroy every Original not yet moved to the new key. Correct the §11 row.
High

F-03 · The author binding is under-specified where attackers aim

P2.2, P5.1–P5.3, key policy, P7.7
Issue
Five gaps. (1) The DID version need not be signed, so whoever packages the evidence can pick any DID version in which the key was valid. (2) Matching a key in updateKeys to a DID verification method is undefined: the method could be JWK, a different encoding, or a relative id. (3) No rule says whether a verification method held in another DID, or a DID’s controller property, confers authority. (4) assertionMethod is only SHOULD, so verifiers will disagree. (5) Nothing fixes the author at genesis: a key listed in two DIDs can silently re-attribute later entries. DID methods without history, such as did:web, or keys that cannot rotate, such as did:key, are not excluded.
Failure scenario
A packager picks an old DID version that still lists a revoked key. Or a key shared by a personal and an organization DID moves authorship of an Original from one to the other mid-history.
Recommendation
  • The signed state MUST include the author DID, the absolute verification method id and the exact DID versionId.
  • The verification method MUST be embedded in that DID version under assertionMethod, with controller equal to the author DID, type Multikey, and publicKeyMultibase byte-identical to the updateKey. Neither a DID controller property nor an external verification method may confer authority.
  • Fix the author DID at genesis and restrict baseline author DIDs to methods with verifiable history (initially did:vh). Make assertionMethod a MUST, and define “controller cycle” in P7.7 or remove it.
Medium

F-04 · Generic did:vh resolution disagrees with Originals verification

§3, §2 state, P5.4, P5.7, P6.5
Issue
VH lets a profile add constraints, and generic resolvers ignore parameters they don’t implement. Author binding, the fixed resource set and P5.7 therefore exist only in verifiers that implement Originals.
Failure scenario
After the F-02 lock attack, or an author mistake, a generic did:vh resolver returns a valid current DID document while Originals rejects the history. A third-party UI showing “DID resolves” misleads users.
Recommendation
  • Add P3.5: a successful generic VH or did:vh resolution MUST NOT be reported as Originals verification.
  • Require deactivation to be expressed as VH deactivated: true, and reject any mismatch with the manifest lifecycle field.
Medium

F-05 · Freshness of identity evidence is unaddressed

P7.6, P5.6, §11 malicious-host row
Issue
P7.6 and §11 consider only stale prefixes of the asset log. Revocation is visible only in the author’s DID history, which may come from the same host or package.
Failure scenario
A host serves the current asset log, including the thief’s entry, with a DID history cut off before Alice removed K1. Every check passes and no freshness warning fires.
Recommendation
  • Add P7.8: the report MUST state the latest author DID version used and whether its freshness was independently established. “Currently authorized” requires identity evidence meeting the freshness policy.
  • Verifiers SHOULD remember the highest verified version for each author DID and each Original, and apply VH’s “Comparing Copies of a Log” to both. Add stale identity history to the §11 host row.
Medium

F-06 · Signing oracles and cross-protocol confusion through a shared assertionMethod key

P5.2, P5.3, key policy, §11 host-application row
Issue
Replay across logs is blocked by VH hash chaining, so one key across many Originals is not a replay risk. The risk is elsewhere: VH fixes the cryptosuite (eddsa-jcs-2022) and proof purpose (assertionMethod), the same ones used for credentials, so nothing in the proof separates domains. P5.2’s parse-and-display is only SHOULD.
Failure scenario
A wallet or agent API that makes eddsa-jcs-2022 assertionMethod proofs over JSON supplied by the caller, or raw Ed25519 signatures over arbitrary bytes, can be used to sign a valid asset entry.
Recommendation
  • Make P5.2’s parse, display and refusal requirements MUST for any signer holding an Originals key.
  • Use a dedicated verification method for Originals entries only.
  • Consider requiring an Originals domain value in the proof. VH lists proof fields only “at minimum”; confirm against eddsa-jcs-2022 implementations.
  • Narrow the §11 claim to conforming signers with dedicated keys.
Medium

F-07 · Deactivation and freezing are not tied to VH semantics

§6 Deactivate, P6.5, D1, D5
Issue
“Terminal state” is not defined as VH deactivated: true. Freezing is not mentioned, although VH allows it and it is irreversible. Under did:vh, a deactivated DID’s document is not returned, so the final manifest may be unreachable through standard resolution. The effect of deactivating the author’s own DID on that author’s Originals is unspecified.
Failure scenario
An author deactivates their DID. Readers disagree on whether that author’s Originals remain editable by naming older DID versions.
Recommendation
  • Amend P6.5: deactivation MUST be VH deactivated: true, and the manifest lifecycle field must equal it.
  • Report freezing as a distinct status. Entries naming a DID version, when the latest author DID is deactivated, are non-current.
Low

F-08 · “Exactly one signature” is not normative

§5 intro, P5.1
Issue
VH’s proof field is an array. Nothing forbids extra proofs or says which proof carries the author binding. How proof.verificationMethod is written is also unpinned.
Failure scenario
Two verifiers evaluate different proofs in the same entry and reach different results.
Recommendation
  • Require exactly one proof and evaluate the binding against it. Pin the verificationMethod form (for example did:key) and reference the author’s method only in the state, so generic resolvers never resolve external identities.
Low

F-09 · P5.7 and P7.7 are loosely defined

P5.7, P7.7
Issue
“Unknown security-relevant fields” leaves each implementation to decide what is security-relevant. VH and did:vh are clearer: they define a closed set of parameters. P7.7’s “no partial success” is stricter than VH, which returns the last valid prefix, and “controller cycles” is undefined.
Failure scenario
Implementations differ on which unknown fields to reject.
Recommendation
  • Reject any member of parameters, proof or Originals-defined state that the pinned VH, did:vh or Originals profile doesn’t define.
  • State that the P7.7 behavior intentionally differs from VH.
Low

F-10 · P8.5 restates VH retrieval rules incompletely

P8.5
Issue
The list in P8.5 reads as complete but omits VH’s percent-decoding rules, IP-literal checks and localhost refusal, and doesn’t require connecting to the validated address, which leaves DNS rebinding open. VH recommends a 5 MiB cap. Each entry carries the full state, so a long-lived Original’s log can exceed that cap, and photographs exceed it on their own.
Failure scenario
A crafted locator gets past the shorter list. A healthy Original becomes unresolvable at default limits.
Recommendation
  • Require every rule in VH’s “Retrieving Log Resources” and connection to the validated address only. Set separate caps for log files and resources in the profile.
Low

F-11 · Content safety covers hosts only

P9.7
Issue
The local SDK and Boop clients also render resource bytes and author-supplied names and metadata, for example in webviews.
Failure scenario
A malicious name or SVG runs script in a desktop or mobile client.
Recommendation
  • Extend P9.7 to any SDK consumer that renders resources or manifest strings, including escaping of strings.
Info

F-12 · The author keeps full power after a sale

P9.6, key policy, §11, D7
Issue
After an inscription is transferred, the author can still edit or deactivate the Original, and could show the buyer one branch and everyone else another. P2.1 detects that only if both branches are seen.
Failure scenario
A buyer believes they control what they bought.
Recommendation
  • Name the selling author as an adversary in §11 and D7 so product copy doesn’t imply transferable control.

Other gaps

  • Importing an older prefix that doesn’t conflict over a newer local history. P7.5 forbids only conflicting branches, so a rollback isn’t covered.
  • The effect on an author’s Originals of losing or erasing the author’s DID log.
  • Log growth when every entry carries the full manifest (see F-10).

Corrections to §11

  • Stolen author key: “cannot act after the asset log rotates” is overstated. The thief can act before the rotation by deactivating, freezing or locking (F-01, F-02).
  • Malicious host: it can also serve stale author DID history (F-05).
  • Malicious host application: the claim holds only if P5.2 becomes MUST and the key is used only for Originals (F-06).
  • Malicious content author: the claim holds only for hosts (F-11).
  • Network attacker: the claim holds only if P8.5 adopts the full VH rule set (F-10).

Strengths worth keeping

  • ✓Storage, inscription and wallet possession never confer edit authority (§2, P9.6).
  • ✓A missing or failed binding never falls back to trusting the key alone (P5.4, P5.6).
  • ✓The verification report is split by dimension, and claimed time is kept separate from proven ordering (§3, §7, P7.6).
  • ✓There is no silent rebase or re-signing on conflict or retry (P4.5, P6.4, P9.6).
  • ✓VH hash chaining and SCID binding mean one key reused across Originals can’t replay entries between them.
  • ✓The legacy CEL boundary is clean (P10.1–P10.4), and archive hardening and limit failures are explicit (P7.5, P7.7).

Recommended priorities

  1. Before the local slice: F-03 (pin the binding), F-02 (constrain updateKeys), F-08 (one proof).
  2. Decide the key-compromise model: either prerotation on asset logs, or witnesses with a check against the latest DID state, plus the rotation order in F-01. This is the main open design question.
  3. Before hosted publication: F-04, F-05, F-07, F-10, F-11, and correct §11.

Scope and method

An independent reviewer, who had not seen the earlier review or the edits, reviewed SPEC.md adversarially against the VH Log spec (local checkout at f2f9fda), the did:vh pre-draft and the SDK. I then checked the VH Log claims the findings rely on: the proof rules, deactivation and freezing, versionTime bounds, retrieval rules, and profile-specific parameters. Points marked plausible in the source review (the Originals proof domain field in F-06, and DID Core behavior in F-03) should be checked against implementations.

## Wire format (partly provisional)

This section pins the byte-level choices that independent implementations must share. D6 decides the 350,000-byte inscription limit and the did:btco network prefixes in P14.12, and D4 the limits in P14.13. D4 decides JCS canonicalization (P14.3); D10 the log format (P14.27–P14.29), which `did:og` defines itself with the entry shape, SCID and entry-hash algorithms of VH Log [S2] and did:vh [S3]; SHA-256 multihashes for resource digests (P14.7, P4.2); the one cryptosuite (P14.8, P5.12); and the parts of P14.2, P14.3, P14.5, P14.8 and P14.10 that it records as decided. D3 decides that an asset log has no witness file (P14.2, P9.8). D6 decides the inscription body, metadata and media type in P14.12 (P9.17, P9.30), except the metaprotocol value, the metadata’s `signers` and `part` members and the asset state’s `network` and `body` members, which are provisional (21 November 2026), and the 8,192-byte preview limit in P14.13, except the JSON-to-CBOR mapping of the metadata, which stays provisional, and that a did:btco signer version is identified by its own metadata alone (P14.12, P5.13). The carried-log values (P14.14–P14.17) are proposed and provisional. The members for signer sets, parent Originals, scoped grants and read grants (`authors`, `parent`, `readers`, a grant’s `scope` and an `author` array) are not part of `did:og` 1.0 and are rejected under P14.4; they are in the experimental additions document (D13). The report form (P14.25) and the test vectors (P14.26) are provisional. Everything else in this section, including the entry state fields and the evidence package format, is **provisional**: it is taken from the Originals SDK at revision 1b3cabdd [S29], which is the only implementation, and recorded so that it is reviewed as a decision rather than adopted silently (D1, D4). Where the SDK and this section differ, this section says so and the SDK is expected to change. A provisional value may still change before an interoperable release. Until then the `method` value is `og:1.0-draft.N`, and N increases by one with every change to this specification that alters which entries, logs or inscriptions are valid, or what a verifier reports for them; Originals written under an earlier draft value are verified only by implementations of that draft. At the interoperable release the value is frozen as `og:1.0`, and after it any such change takes a new `method` value.

### Log and parameters

P14.1 An Original’s asset log MUST use the `method` value `og:1.0-draft.1`. A verifier MUST reject a log whose `method` value is not one it implements, and an implementation of this draft implements `og:1.0-draft.1` only: a log, package or inscription written under another value, such as `originals:1.0` of the earlier drafts, gets outcome `unsupported` (P7.18), never `verified` or `invalid` under this draft. The genesis entry’s parameters MUST be exactly `method`, `scid` and `updateKeys`, with `updateKeys` the empty array `[]`. A later author entry’s parameters MUST be `{}` or exactly `{"updateKeys": []}`, and a deactivation entry’s (P6.5) exactly `{"deactivated": true}` or `{"deactivated": true, "updateKeys": []}`. An editor entry’s parameters MUST be `{}`; an editor entry MUST NOT carry `updateKeys`. In this version `updateKeys` MUST be `[]` wherever it appears, and a verifier MUST reject an entry whose `updateKeys` has any other value; a non-empty value is reserved for a later method version, which may use it to restrict which of the author DID’s keys may sign (D7). `updateKeys` confers no authority in `did:og`: an entry is authorized only by its signer’s DID at the version the entry names and, for an editor, by the grant in its predecessor (P5.3, P5.16), never by a key in the asset log’s own parameters. A processor for VH Log or did:vh would read an empty `updateKeys` as a log that no key may update, so it cannot apply this profile (P3.5). A verifier MUST reject a null parameter value, and any parameter this rule does not list (P5.9, P9.9; decided 21 November 2026).

P14.2 The asset log file is named `did.jsonl`. Each entry is one line of compact JSON ending in a single line feed. An asset log has no witness file (P9.8). `versionTime` MUST carry at most three fractional digits and end in `Z`, and MUST be later than the previous entry’s by at least one millisecond (D5). A reader MUST reject an asset log, hosted or packaged, that breaks this line format, including one with a carriage return or no final line feed, or whose line contains whitespace outside JSON strings. Key order and string escapes are not constrained, because hashes and proofs are computed over the JCS form (P14.3). The logs of signer DIDs and did:webvh aliases follow their own DID methods.

P14.3 Canonicalization is JCS [[spec: RFC8785]]. Parsers MUST reject duplicate keys, lone surrogates, any number whose exact decimal value, as written, has magnitude greater than 9,007,199,254,740,991 (2<sup>53</sup> − 1) (for example `1e16` or `9007199254740993.0`), any number whose value is negative zero (for example `-0` or `-0.0`), and nesting deeper than 64 levels (P5.7).

P14.27 Each entry of an asset log is a JSON object with exactly the members `versionId`, `versionTime`, `parameters`, `state` and `proof`, the entry shape of VH Log [S2] and did:vh [S3]. `versionId` is the entry’s version number, starting at 1 for the genesis entry and increasing by one with each entry, in decimal with no leading zero, followed by a hyphen-minus `-` and the entry hash (P14.29). `versionTime` is a string as P14.2 fixes it. `parameters` is an object as P14.1 fixes it. `state` is the entry state (P14.4). `proof` is an array holding exactly one proof (P14.8). A verifier MUST reject an entry with any other member, without one of these, or with a member of another type, and MUST reject a log whose version numbers do not run 1, 2, 3 and so on in line order (P14.2).

P14.28 The SCID is `base58btc(multihash(JCS(p)))`, where `multihash` is SHA-256 written as the multihash code 0x12, the length 0x20 and the 32-byte digest, `base58btc` is the base58 encoding with the Bitcoin alphabet and no multibase prefix, and `p` is the genesis entry as prepared before publication: without `proof`, with `versionId` the string `{SCID}`, and with the string `{SCID}` in place of the SCID wherever it will appear, which is in the `scid` parameter and in `state.id`, `did:og:{SCID}`. A verifier MUST verify the SCID: take the genesis entry, remove `proof`, set `versionId` to `{SCID}`, replace every occurrence of the `scid` parameter’s value in the entry, in every string, with `{SCID}`, and compute the hash above over the JCS form (P14.3) of the result; a result that differs from `scid` MUST be rejected. SHA-256 is the only hash algorithm: a verifier MUST reject an SCID or entry hash whose multihash names any other algorithm or length.

P14.29 The entry hash of an entry is `base58btc(multihash(JCS(e)))`, with `multihash` and `base58btc` as in P14.28, over the entry `e` without `proof` and with its `versionId` replaced by the predecessor’s `versionId`, or, for the genesis entry, by the SCID. A verifier MUST reject an entry whose `versionId` is not its version number, `-` and its entry hash. Because the hash covers the predecessor’s `versionId`, each entry names its parent, and two entries with the same predecessor are a fork (P6.6). These algorithms, with P14.2 and P14.3, give the same SCID and entry hashes that VH Log at [S2] and did:vh at [S3] compute for the same bytes, so a library for those logs can parse an asset log and check its hash chain; it cannot verify it, which only this profile does (P3.5, P14.1).

### Entry state

P14.4 An entry’s state MUST have exactly the members `id`, `operation`, `author`, `asset` and `transitions`, an editor entry also `editor`, and an author entry MAY also have `supersedes`. Every object defined in this section MUST have exactly its listed members, and a verifier MUST reject any other member (P5.7).

- `id` is the Original’s `did:og`, `did:og:<SCID>`.
- `operation` is `create` in the genesis entry and `update` or `deactivate` in every other entry. Anchoring is an `update` (P9.10).
- `editor` and `author` are each a [[ref: signer]] reference, exactly `{did, verificationMethod, versionId}`, all strings (P5.1, P5.16). For a did:btco signer, `versionId` is the inscription id of the version (P5.13).
- A verifier MUST reject an `author` that is not an object, such as an array of signer references (D13).
- `asset` has the required members `name`, `status`, `network`, `resource` and `aliases`, and the optional members `metadata`, `editors`, `preview` and `body`. A verifier MUST reject `authors`, `parent` and `readers`, which only the experimental additions define (D13).
- `supersedes` is an array of 1 to 8 versionIds, all strings and all different, naming the entries an author entry supersedes (P6.9). An editor entry MUST NOT have it. Its name and limit are provisional.
- `transitions` is an array of `{from, to}` with at most one item, where `from` is the previous digest, or null in the genesis entry, and `to` is the new digest. It MUST have one item exactly when the resource’s digest or mediaType changes: in the genesis entry `{from: null, to}`, and in a later entry that changes either `{from, to}`, where `to` equals `from` when only the mediaType changes (P14.6). It is empty in any other entry, including a deactivation (P4.1, P4.2).

P14.5 The members of `asset`:

- `name`: a string of 1 to 1,024 UTF-16 code units.
- `metadata`: a JSON object. When absent, there is no metadata (P4.6).
- `status`: `active` or `deactivated`, agreeing with the operation and the deactivated parameter (P6.5).
- `aliases`: an array of DIDs with at most one did:webvh and at most one did:btco. It holds no DID of any other method and no DID twice, and a verifier MUST reject one that does (P3.9). The genesis entry lists none.
- `network`: the Bitcoin network on which the Original can be anchored (P9.34): `mainnet`, `signet`, `testnet` or `regtest`, matching a did:btco DID with no prefix, `sig:`, `test:` or `reg:` respectively (P9.10). The genesis entry sets it, and every later entry MUST carry it unchanged. Its name and values are provisional.
- `resource`: the descriptor of the Original’s one resource, at its version in this entry (P4.1).
- `body`: the inscription body mode that the entry signs (P9.17): `preview`, `full` or `none`. It is present exactly in the entries whose `aliases` list a did:btco DID, and is `preview` exactly when `preview` is present (P9.30). Its name is provisional.
- `preview`: exactly `{mediaType, size, digest}`, the preview of the version that `resource` names, for an inscription (P9.30). Each member follows P14.6 and P14.7 as for a resource descriptor, and `size` MUST be at least 1 and at most 8,192. It is allowed only in an entry whose `aliases` list a did:btco DID.
- `editors`: an array of 1 to 32 grants, each with exactly the members `did`, `name`, `metadata` and `resource`, all but `did` booleans. An empty array MUST NOT be used; absence means no editors (P5.15). A grant with a `scope` member is rejected, as any other member is (P14.4).

P14.6 A resource descriptor is exactly `{mediaType, size, digest}`. `mediaType` is a `type/subtype` media type without parameters, and a verifier MUST reject one that has a parameter. `size` is the byte length, a non-negative integer. `size` MUST NOT change unless `digest` changes in the same entry. `mediaType` MAY change with `digest` unchanged: that is a new version of the resource with the same bytes, and its entry carries a transition whose `from` and `to` are both that digest (P4.1, P4.4, P14.4; decided 21 November 2026, replacing the rule that `mediaType` changes only with `digest`).

P14.7 A resource digest is the letter `z` followed by the base58btc encoding of the SHA-256 multihash (code 0x12, length 0x20) of the bytes, so it begins `zQm`. A verifier MUST reject a digest whose encoding is not the one this produces (P4.2). The asset log’s own hashes, the SCID and entry hashes (P14.28, P14.29), are the same multihash without the `z`.

### Proofs and keys

P14.8 Each entry has exactly one proof, by its signer (P5.2), and the entry’s `proof` array holds that one proof (P14.27). The proof has `type` `DataIntegrityProof`, `proofPurpose` `assertionMethod`, a `cryptosuite` of `eddsa-jcs-2022` (P5.12), a `verificationMethod` byte-identical to the signer reference’s, and a `proofValue` of `z` followed by the base58btc encoding of the 64-byte signature. The proof is computed over the entry without its proof. The proof is the one `eddsa-jcs-2022` defines: the Ed25519 signature over the SHA-256 hash of the JCS form of the proof without `proofValue`, followed by the SHA-256 hash of the JCS form of the entry without its proof. Signer keys are Ed25519 Multikeys in base58btc, with prefix 0xed01 and 32 bytes; a verifier MUST reject a key of any other type or length. Ed25519 verification MUST reject small-order points and non-canonical encodings. A proof has exactly the members `type`, `cryptosuite`, `verificationMethod`, `proofPurpose` and `proofValue` (P14.4).

### Derived DID document

P14.9 The DID document derived for each version of an Original’s `did:og` (P3.8) is exactly:

```json
{
  "@context": ["https://www.w3.org/ns/did/v1"],
  "id": "did:og:<SCID>",
  "controller": "<author DID>",
  "alsoKnownAs": ["<aliases, omitted when empty>"],
  "service": [{
    "id": "did:og:<SCID>#files",
    "type": "OriginalsFiles",
    "serviceEndpoint": { "mediaType": "…", "size": 0, "digest": "z…" }
  }]
}
```

`controller` is the author DID string. The grants are not in the derived document. The `#files` service is the resource’s descriptor at that version; where to fetch the bytes comes from a did:webvh alias, a `src` location, an evidence package, a carried file (P7.11) or, for a version inscribed in full on the anchoring sat, that inscription’s body (P9.17). The `preview` member (P14.5) is not in the derived document.

### Evidence package

P14.10 An evidence package is a ZIP archive whose entries are all stored without compression. Names are at most 255 bytes of UTF-8. A writer MUST produce entries sorted by name, compared as UTF-8 bytes, with the date 1980-01-01 00:00, the UTF-8 name flag and Unix mode 0100644, so that the same contents give the same bytes; a reader MAY ignore the order, date and flags, but MUST decode every name as UTF-8, reject a name that is not valid UTF-8, and reject an entry whose mode is not a regular file (P7.5). The exact bytes a writer produces are provisional (21 November 2026), and are these: for each entry in order, a local file header followed by the stored bytes, with no data descriptor; then a central directory header for each entry, in the same order; then one end of central directory record. Every header has version needed to extract 10, general purpose flags 0x0800 and only that, compression method 0, time 0x0000, date 0x0021, the CRC-32 and both sizes of the bytes, an empty extra field and, in the central directory, an empty file comment, version made by 0x0314 (Unix), disk number 0, internal attributes 0 and external attributes 0x81A40000. The archive has no directory entries, no ZIP64 records, no archive comment, and nothing before the first local header or between its parts. The vectors (P14.26) are built this way. It contains:

- `originals-evidence.json`, the manifest: exactly `{format, profile, original, checkpoint, head, completeness, missing}`, all members required, where `format` is `originals-evidence/0.1`, `profile` is the asset log’s `method` value, `og:1.0-draft.1`, `original` is the Original’s `did:og`, `checkpoint` is the versionId of the target checkpoint (P7.1) and `head` the versionId of the last entry of `asset/did.jsonl`, both strings, `completeness` is `complete` or `partial` (P7.1) and describes the package through `checkpoint`, and `missing` is an array, empty when nothing is missing, of `{kind: "resource", version, digest, versionId}` and `{kind: "identity", did, role}` items: `version` is the resource’s version number (P4.4), an integer from 1, `versionId` is that of the entry that introduced the version, and `role` is `author` or `editor`. `checkpoint` MUST be the versionId of an entry in `asset/did.jsonl`, which is `head` or an entry before it, and a reader MUST reject a manifest that breaks any of these rules. Its bytes are its JCS form (P14.3) in UTF-8, with no byte order mark and no final line feed; a reader MUST accept any JSON with these members and values. The manifest’s types, and its bytes, are provisional (21 November 2026);
- `asset/did.jsonl`, the asset log;
- `signers/<hex SHA-256 of the DID>/did.jsonl`, the hex being the lowercase hexadecimal of the SHA-256 of the DID string in UTF-8, and `did-witness.json` where that DID’s log uses witnesses, for each did:vh or did:webvh signer; did:btco signers are read from Bitcoin and are not packaged (P9.18);
- `resources/<digest>`, the bytes of each version of the resource included.

A preview (P9.30) is not a version of the resource: a writer MUST NOT put one under `resources/` or list it in `missing`, and a package without previews can be complete. A preview’s bytes are read from the inscription that carries it, and verifying the log does not need them.

Import MUST apply P7.5, with at most 20,000 archive entries and 512 MiB in total.

The SDK names the signer directory `authors/` and writes an `asset/did-witness.json`; this section uses `signers/` and none, because editors are signers too and asset logs have no witnesses.

### Hosting

P14.11 A did:webvh alias is a did:webvh log of its own whose DID document lists the Original’s `did:og` in `alsoKnownAs` (P3.6). Relative to that alias’s location, the host serves the evidence package unpacked under `originals/`, and serves each resource with its signed media type and the headers P9.7 requires.

### Bitcoin

P14.12 An Originals inscription has exactly these fields, and no other (P9.17, P9.31):

- **Metaprotocol** (ord tag 7): the UTF-8 string `og`. This value is provisional.
- **Metadata** (ord tag 5): the CBOR encoding of a JSON object with the member `entries` and, where they apply, the members `signers` and `part`, and no other member. `entries` is an array of asset log entries, each the parsed JSON of one asset log line, in order (P9.32): across the parts of the anchoring publication they are the entries from genesis through the anchoring entry, and across the parts of a later publication exactly one entry; a part other than the final part may hold none. `signers` is a non-empty array of objects, each with exactly the members `did` and `log`, and also `witness` where the DID’s method requires witness proofs for the versions in `log`: `did` is a did:vh or did:webvh DID, at most once in the array; `log` is a non-empty array of that DID’s log entries, each the parsed JSON of one line of its `did.jsonl`, continuing its inscribed signer history (P9.33); `witness` is the array of items of its `did-witness.json` for those versions. `part` is present exactly in a publication in parts, as an array of two integers `[i, n]`: the part’s position, counting from 1, and the number of parts (P9.32, P14.13). The metadata is split into data pushes of at most 520 bytes, which a reader concatenates before decoding.
- **Content type** (ord tag 1): as the last entry’s `body` requires (P9.17): the `mediaType` of its `preview` for `preview`, the `mediaType` of its `resource` for `full`, and none for `none`; and none in any part but the final one.
- **Body**: as the last entry’s `body` requires: the exact bytes of the preview that its `preview` names, the exact bytes of the resource version that its `resource` descriptor names, or no body; only the final part of a publication may have one (P9.17, P9.30, P9.32). A body never has a content encoding. An inscription has a body when its envelope has the empty data push that begins ord’s body, even if no bytes follow it, and has no body when it has no such push. An inscription with no body and only fields is valid in ord and is still an inscription.

In particular, an Originals inscription never names a delegate (ord tag 11), a pointer (tag 2) or a parent (tag 3), never has a content encoding (tag 9), and carries no field that the ord release line [S31] does not recognise; a verifier MUST reject one that does, together with its publication (P9.17, P9.31). The rule against delegates is provisional.

ord’s curse status does not affect an Originals inscription. ord 0.29.x gives the duplicate-field curse to an inscription whose metadata takes more than one data push, as all metadata over 520 bytes does, and marks every inscription on a sat after its first as a reinscription; from ord’s jubilee height (824,544 on mainnet, 110 on regtest) it numbers such inscriptions as vindicated rather than cursed. A verifier MUST NOT reject an Originals inscription, or treat it differently, because ord reports it as cursed, vindicated or a reinscription. Because a pointer is forbidden, a writer places an inscription on the anchoring sat by making the envelope’s input the reveal transaction’s first input, spending an output whose first sat is the anchoring sat: ord assigns an inscription to the first sat of the input that carries it. For a publication in parts, each part’s reveal can send the sat, at offset 0, to the taproot output that commits to the next part’s script, as `vectors/regtest/` does (informative; regtest gate, 21 November 2026).

The JSON-to-CBOR mapping is provisional; it is the one ord applies to `--json-metadata`: an object is a map with text-string keys in the object’s order, an array an array, a string a text string, an integer an integer in shortest form, any other number a float in the narrowest of half, single and double precision that holds it exactly, `true`, `false` and `null` their simple values. A reader MUST accept a float of any of the three widths, and MUST reject metadata that is not one well-formed CBOR item, or that contains a tag, a byte string, an indefinite-length item, a map key that is not a text string, a duplicate key, an integer outside P14.3’s bound, or a float that is not finite, is negative zero or has a magnitude outside P14.3’s bound. Because each entry is checked over its JCS form, the width of a float and the form of an integer do not change its hashes or proof. So that the same publication gives the same bytes, a writer MUST write the metadata’s members in the order `entries`, `signers`, `part`, each `signers` item’s in the order `did`, `log`, `witness`, and each entry and signer log entry with its members in the order of its JCS form, and MUST write the envelope’s fields in the order ord 0.29.1 writes them [S31]: content type, then metaprotocol, then the metadata pushes, then the body; a reader MUST accept members and fields in any order that ord accepts. This writer order is provisional (21 November 2026). It decodes the metadata to JSON values, and each entry is then checked under P14.3–P14.8, its hashes and proof computed over its JCS form, and each signer log entry under its own DID method (P9.33); P14.2’s line format does not apply to either. An entry over the entry limit (P14.13) is measured as its JCS form in UTF-8. The metadata and body together MUST NOT exceed 350,000 bytes. An Originals inscription whose metadata does not decode to such an object MUST be rejected; an inscription without the `og` metaprotocol is not an Originals inscription, whatever its metadata (P9.31). A did:btco DID matches `^did:btco:((sig|test|reg):)?(0|[1-9][0-9]{0,15})$` with a sat number no greater than 2,099,999,997,689,999 (P9.10). A did:btco signer version is an inscription whose own metadata is a CBOR DID document, in shortest-form encoding, whose `id` is that DID, whatever its body, delegation or content encoding (P5.13).

### Limits

P14.13 A verifier MUST enforce these limits (P7.7, P8.5):

| Limit | Value |
|---|---|
| Entries in an asset log | 10,000 |
| Bytes in one entry, as its JCS form in UTF-8, in every format | 65,536 |
| Editor grants | 32 |
| Entries named in one `supersedes` (P6.9) | 8 |
| Inscriptions in one publication (P9.32) | 16 |
| Bytes in a preview (P9.30) | 8,192 |
| Versions of one signer DID | 1,000 |
| Bytes in a fetched log file | 16 MiB |
| Bytes in one fetched resource | 64 MiB |
| Time for one fetch | 15 seconds |

The SDK MUST refuse to sign an entry over the entry limit, rather than produce one every verifier rejects. An inscription’s 350,000 bytes (P9.17) hold its body, its entries and the signer history it inscribes together, and a publication too large for one inscription uses up to 16 (P9.32). With a preview of at most 8,192 bytes, the log through the anchoring entry has room for over 340,000 bytes, whatever the size of the resource. A full version leaves little room for the log: a version over about 340,000 bytes cannot be inscribed in full. Either way, authors SHOULD anchor early, while the log through the anchoring entry is still short.

The SDK measures entry size in UTF-16 code units of the re-serialised entry and sets no resource-size limit; this section measures the UTF-8 bytes of the entry’s JCS form and sets 64 MiB, so that implementations in other languages agree.

### Shared-host saves

A shared host (P6.7) needs no particular transport. As a guide, the SDK submits `{original, entry, resources, identities}`, where `entry` is the exact line, and the host answers `accepted` or `already-accepted` with the checkpoint and head, or `stale-parent` with the head.

### Carried log (proposed)

Everything in this subsection is provisional. The trailer media types were checked only on macOS (Preview, Quick Look, `sips`, `afinfo`) with a 12,000-byte trailer; adding a media type needs the same evidence across the readers it targets.

P14.14 The carrier for a resource version is chosen by the `mediaType` its descriptor names (P14.6), compared ASCII case-insensitively, and no other carrier is valid for it (P7.12). A `mediaType` has no parameters (P14.6), so one such as `text/plain; charset=utf-8` is rejected, not matched with its parameter ignored:

| Carrier | `mediaType` |
|---|---|
| Trailer (P14.15) | `image/png`, `image/jpeg`, `image/gif`, `image/tiff`, `image/heic`, `audio/mp4`, `audio/wav`, `audio/aiff` |
| Text block (P14.16), with the comment syntax in its table | the media types in P14.16’s table |
| JSON member (P14.17) | `application/json`, `application/geo+json` |

Any other media type has no carrier, including an alias of a listed type, such as `application/javascript` or `audio/x-wav`; ZIP-based formats such as EPUB and Office documents, whose readers look for their directory only in the last 65,557 bytes; PDF, whose readers may look for `%%EOF` only in the last 1,024 bytes; and other `+json` types, whose own signatures or closed schemas an added member can break.

A carrier is at most 16 MiB (16,777,216 bytes); a larger one is no carrier. In every carrier an entry’s size is measured as its JCS form in UTF-8 (P14.13); the limits on a file, a carrier and an inscription are separate from it. In every carrier each entry is checked under P14.3–P14.8, nesting depth counted from the entry. A reader MAY refuse a carried file larger than the resource limit of P14.13 plus 16 MiB.

A reader does not know the media type before it has found the log. It tries each carrier’s detection, and no two carriers can match one file. A file name extension or a declared type MAY decide which it tries first, but is only a hint: when the hint is wrong or absent the reader tries the other carriers. It then verifies the log and checks that the carrier it found is the one this rule assigns to the last entry’s `mediaType` (P7.12).

P14.15 A trailer is the asset log `L`, exactly as P14.2 defines `did.jsonl`, followed by a 24-byte footer: the byte length of `L` as an unsigned 64-bit big-endian integer, then the 16 bytes `89 4F 52 49 47 49 4E 41 4C 4C 4F 47 0D 0A 1A 0A` (`\x89ORIGINALLOG\r\n\x1A\n`). A file has a trailer only if it is at least 24 bytes long, its last 16 bytes are that sequence, and `24 + length`, computed without overflow, is at most 16 MiB (P14.14) and at most the file’s size. A reader can decide this from the footer alone, before reading `L`. The carrier is the last `24 + length` bytes, and the resource version is every byte before it. Like PNG’s signature, the footer is damaged by end-of-line conversion and by stripping the high bit, so a file altered that way has no trailer rather than a wrong one. A trailer whose `L` breaks P14.2 is a trailer with an invalid log.

P14.16 A text block is a single line feed (0x0A), which a writer never precedes with a carriage return of its own, followed by these lines:

- the comment opener, for a block comment;
- `=====BEGIN ORIGINAL=====`;
- one line per entry, in order, each the compact JSON of the entry as in P14.2;
- `=====END ORIGINAL=====`;
- the comment closer, for a block comment.

For a line comment, each marker and entry line starts with the comment prefix and one space. Each line ends in a line feed, or in CR LF when the resource version’s own lines end that way; a reader MUST accept either. A writer ends the last line too, but a reader MUST also accept a last line with no line end. A writer MUST refuse a text block unless the resource version is valid UTF-8, a leading UTF-8 byte order mark allowed. A writer MUST place the block only where the host format’s parser reads it as a comment: parsed under the version’s own syntax, the appended block MUST be a separate comment and nothing else, and a writer MUST refuse otherwise, or when it has no parser for that syntax. `text/plain` has no comment and no such check. The test is the parse of the resulting file, not a search of the version for particular text, and no list of refusals stands in for it.

For example, and not normatively, a writer refuses: an HTML version that ends inside a comment, an open tag, a processing instruction, or an element whose content is not parsed as markup, such as `script`, `style`, `iframe`, `noembed`, `noframes`, `textarea`, `title`, `xmp`, `plaintext` or `noscript`; a Markdown version that ends inside an unclosed code fence, or in one of those HTML contexts; an XML version, including XHTML and SVG, that ends inside a comment, a CDATA section, a processing instruction or an open tag; a CSS version that ends inside an unterminated comment or string; a YAML document whose last node is a block scalar; and a version of a line-comment type that ends inside an unterminated string, heredoc or block comment, or whose last line ends in a line continuation. An unclosed HTML `pre` is no reason to refuse: its content is parsed as markup, so the block is still a comment.

Every entry line MUST be ASCII: a writer escapes every other character inside JSON strings with `\u` escapes, and also escapes characters so that no line contains the comment’s closer or, for `<!--` comments, `--`. These escapes do not change the entry’s JCS form (P14.3), and P14.2’s line rules otherwise apply to each entry line once its comment prefix and line end are removed. A reader MUST treat as no carrier a block in which any line contains a character that is not ASCII, a carriage return other than before its line feed, the comment’s closer before the closer line or, for `<!--` comments, `--` outside the opener and closer lines, so that a value un-escaped after signing cannot end the comment early.

A reader finds the block from the end of the file. After removing any spaces, tabs, carriage returns and line feeds at the end, the last line MUST be the comment closer for a block comment, or the `=====END ORIGINAL=====` line otherwise; the block then runs back through entry lines to the nearest `=====BEGIN ORIGINAL=====` line and, for a block comment, the opener line immediately before it. Marker, opener and closer lines match only as whole lines, after their comment prefix and line end are removed. The block is located by these lines alone: a line between the markers that is not a valid entry line, or no entry line at all, makes it a text block with an invalid log, not content. A block whose first line is not preceded by a line feed is no carrier. An incomplete or malformed marker structure is no carrier either: a closer line not directly preceded by the `=====END ORIGINAL=====` line, or, in a block comment, a `=====BEGIN ORIGINAL=====` line not directly preceded by the opener line. Removing a carrier MUST restore the version’s exact bytes. Which line end a writer uses for a version with mixed line ends, and whether the carriage-return rule covers the whitespace after the last line, are open (D4). The carrier runs from the line feed immediately before the block’s first line to the end of the file, including the whitespace after its last line, and the resource version is every byte before it. Any earlier block is content.

| `mediaType` | Comment |
|---|---|
| `text/plain` | none: the lines stand alone |
| `text/markdown`, `text/html`, `application/xhtml+xml`, `image/svg+xml`, `application/xml`, `text/xml` | block, `<!--` and `-->` |
| `text/css` | block, `/*` and `*/` |
| `text/javascript`, `application/typescript`, `text/x-c`, `text/x-c++`, `text/x-java-source`, `text/x-go`, `text/x-rust`, `text/x-swift`, `text/x-kotlin` | line, `//` |
| `text/x-python`, `text/x-shellscript`, `application/yaml`, `application/toml` | line, `#` |
| `application/sql` | line, `--` |

Other `text/` types, such as `text/csv`, have no carrier, because a trailing line would be read as content; so has `text/x-ruby`, whose `__END__` makes every later line data.

P14.17 A JSON member is a member of the document’s root object named `originalLog`, whose value is an array of the entries, in order, each a JSON object. A writer MUST write it as the root object’s last member: immediately after the last existing member’s value, before the whitespace that followed that value, or immediately after the root object’s `{` when the object is empty, leaving every other byte unchanged. When the member is the root object’s last, the carrier runs from the first byte after the previous member’s value, or after the root object’s `{` when it is the only member, through the array’s closing `]`, and the resource version is the document with exactly those bytes removed. A document has a JSON member only if its root is an object with exactly one member of that name, member names being compared after their escapes are decoded. A reader MUST reject a root object with more than one, and does not choose among them; a member of that name nested below the root is not a JSON member. A reader MUST find the member wherever it is in the root object, because tools reorder members. A member that is not the root object’s last still carries its log, which is verified and reported as P7.12 states for a log found where no carrier is defined; how its bytes are removed is open (D4), so the file is not verified as a version. A root member of that name is a JSON member whatever its value; a value that is not an array of objects is an invalid log. A reader MUST skip one leading UTF-8 byte order mark, which stays part of the version. A document nested deeper than 1,024 levels outside the entries, counting the root object as level 1, has no JSON member. A reader needs a parser that reports byte offsets to find the carrier’s bytes exactly. Outside the entries the document need only be JSON [[spec: RFC8259]]; P14.3’s limits apply to the entries only. P14.2’s line format does not apply. Whitespace, key order and string escapes in the entries are therefore free, so a carried log survives reformatting, although the remaining bytes then no longer match the version (P7.12). A writer MUST refuse a document whose root is not an object or that has any root member of that name (P7.15).

### Verification report and test vectors

P14.25 A verification report (P7.17–P7.23), when an implementation writes one as JSON, is an object with exactly these members, all provisional (21 November 2026): `type`, the string `OriginalsVerificationReport`; `profile`, the method value it applied (P14.1); `original`, the `did:og`; `checkpoint`, the versionId of the reported checkpoint, or null when `state` is `none`; `evidence`, the evidence set it identifies (P7.17), as `{inputs, network, tip, depth}`, where each input is `{kind, source, digest}` and `digest` is the input’s bytes in P14.7’s encoding, and `network`, `tip` (`{height, hash}`) and `depth` are null when no Bitcoin input was supplied; `axes`, an object with one member per axis of P7.18, each the axis value; `entries`, an array with one `{versionId, status, …}` item per entry considered, in log order, which has `rule` when `status` is `rejected`, and `authority`, `endorsed`, `ordering` and, for `existed-by-block` and `chain-ordered`, `block`, when `status` is `accepted` (P7.19); `signers`, one `{did, role, latestVersionId, source, freshness}` item per signer DID relied on, with `obtained` when the history did not come from Bitcoin (P7.8); `missing`, as in the manifest (P14.10); `dependencies`, the external dependencies P7.21 lists, each `{kind, did}`; and, when `bitcoin` is `anchored`, `bitcoin`, as `{sat, holder, conflictingAnchors, unverifiable, waiting}`, where `holder` is `{address, uniqueness}` and `uniqueness` is `provisional` or `{established-through: <height>}` (P9.11, P9.16). Two reports are the same when their members are equal as JSON values; key order and whitespace do not matter.

P14.26 Provisional test vectors for `og:1.0-draft.1` are in the specification’s repository under `vectors/og-1.0-draft.1/`, with a generator that rebuilds them from fixed seeds and a checker that verifies them independently (`npm run vectors`, `npm run vectors:check`). They are one Original followed through three layers, with its genesis entry on its own: `genesis/`, the genesis entry, the exact JCS bytes its SCID and entry hash are computed over (P14.28, P14.29), its author’s log and resource, an evidence set and the expected report; `local/`, its author’s did:webvh log, a two-entry asset log, the two resource versions, the evidence package and its manifest, an evidence set and the expected report; `hosted/`, the files a host serves under its did:webvh alias (P14.11), and a sequence of shared-host saves (P6.7) that is accepted, refused as a stale parent, and retried as already accepted; and `bitcoin/`, the two Originals inscriptions of its anchoring publication on regtest, in parts (P9.32), with the author’s did:webvh history inscribed (P9.33) and the full version as the body (P9.17), on a synthetic chain fixture, with the evidence set and the expected report. The chain fixture is synthetic: no regtest chain produced its transactions or blocks, and its hashes are placeholders; a scripted run on a real regtest chain is the first step of the mainnet gate (section 13). Beside them, `vectors/prior-format/` holds the two mainnet reveal transactions of the acceptance Original of 1 November 2026, written under `originals:1.0` before `did:og`, which a verifier of this draft reports `unsupported` (P14.1). An implementation of `og:1.0-draft.1` MUST reproduce each vector’s bytes from its inputs where this section fixes them (P14.2, P14.10, P14.12) and MUST produce the expected report from each evidence set (P14.25). Where a vector and this specification disagree, the specification governs and the vector is a defect. The vectors change, with the draft number, whenever a choice they depend on changes (P14.1).

### Unused rule numbers

Rule numbers P14.18–P14.22 are not used. They held encodings for anchoring on an EVM chain, withdrawn when Bitcoin became the only anchor (D6), and are not reused. Rule numbers P14.23 and P14.24 are not used in `did:og` 1.0: they hold the scope types and the read request, which moved to the experimental additions document (D13), and are not reused.

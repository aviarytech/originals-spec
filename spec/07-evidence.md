## Evidence packages and fresh verification

### Retained behavior and new evidence

An evidence package preserves signed history and historical resource bytes so a fresh reader can reconstruct versions. It additionally needs the author identity evidence that binds each signing key to the author’s DID. A public key being present in an archive is not sufficient evidence that an identity authorized it.

An evidence package describes what it includes and what is unavailable. Complete and partial packages must be distinguishable. Offline verification is an intended capability of a complete package, but it depends on specifying portable identity evidence and any freshness or external-ordering requirement.

### Proposed package rules

P7.1 An evidence package MUST declare whether it is complete or partial. A complete package MUST include the VH evidence through the selected checkpoint, the identity evidence required to check each entry’s signer binding, for the author and for every editor that signed an entry, and the historical resource bytes referenced by that prefix. It MUST identify the Original, profile and target checkpoint unambiguously.

P7.2 Packaging MUST preserve signed bytes or canonical signed representations as required by each proof format. Reformatting, normalization or changing an envelope discriminator MUST NOT be presented as preserving an existing signature.

P7.3 A reader MUST validate evidence before exposing derived state as verified. Verification MUST establish identifier/genesis binding, history continuity, log authority, author binding and state transitions, and MUST check the digest of every resource byte sequence it is given. Resource bytes are not needed for the log to verify; missing ones are reported as unavailable content (P7.4, P9.18). A private key MUST NOT be required for any read-only check.

P7.4 Missing bytes MUST produce an explicit partial-availability result identifying the affected resource version and checkpoint. Available bytes MUST still be checked. Missing proof or identity evidence MUST be reported separately from missing content; no missing item permits bypassing a signature or digest check.

P7.5 Import MUST NOT confer signing authority, trust unknown keys, or replace an existing history with a conflicting branch without explicit handling. Untrusted archive paths, sizes and compression MUST be bounded before extraction. Import MUST reject absolute paths, `..` segments, symbolic links and duplicate entries. Import MUST NOT replace a newer local history with an older prefix of it.

P7.6 Evidence from a truncated prefix MUST NOT be represented as the latest state. For an anchored Original, an unverifiable inscription does not stop the accepted state before it being current; the report lists that inscription and any publications waiting on it (P9.15). A valid historical prefix and a current result are separate claims, and off Bitcoin only the first can be made (P7.10). For entries not inscribed on an anchoring sat, reports MUST label time and ordering as claimed only, except that an anchoring inscription shows the entries before it existed no later than its block (P9.16).

P7.7 A verifier MUST enforce profile-defined limits on history length, entry size, identity-history length, the number of editor grants and the number of versions. When a history exceeds a limit, the verifier reports the last valid prefix as VH requires, and MUST label the result limit-exceeded and MUST NOT report it as complete or current.

P7.8 The verification report MUST state, for the author DID and each editor DID it relied on, the latest versionId used and whether its freshness was independently established. An Original that is not anchored is never reported as current or currently authorized (P7.10). For an anchored Original, a verifier checks each did:vh or did:webvh signer against the newest version of that DID it knows of: the newest it has obtained from any source or retained from earlier verification (owner decision, 21 October 2026). It is not required to show that no newer version exists, and the report MUST state that version and when it was obtained. A verifier that knows of a newer version than the one a package or host supplies MUST use the newer one. A did:vh or did:webvh signer’s freshness is independently established only if that DID’s own witnesses or watchers support its latest version (P9.8); for a log obtained without that support, the report MUST state freshness as not established, together with where the log was obtained, when, and its latest versionId (owner decision, 23 October 2026). A verifier MUST NOT treat a did:webvh log fetched from a location as that identity’s latest unless its latest version’s `id` names that location; this does not apply to did:vh logs or to logs from an evidence package. A did:webvh log whose latest version names another location shows that the identity has moved: the verifier MUST still use every verified version in it, including any that removes a key, SHOULD look for the moved log as P5.14 describes, and MUST report freshness as not established until it finds it. A report shown to a person MUST say plainly that the verifier obtained that DID’s history from that place at that time, and that the DID may have a newer version, such as one that removes a key, which the verifier has not seen. did:btco signers are read from Bitcoin (P5.13). Verifiers SHOULD retain the highest verified versionId seen for each author DID and each Original, and compare copies of both logs as VH describes.

P7.9 If the signing key of an entry that is not inscribed on an anchoring sat is not under assertionMethod in the latest verified state of its signer’s DID, or the author DID’s latest verified state is deactivated (P6.5, P5.18), a verifier MUST report that entry as historically authorized only, because it may have been signed after the key was removed or the DID deactivated (section 5), and any result that includes it MUST say so. An entry inscribed on an anchoring sat is checked instead against its signer’s DID state at its inscription time, and an editor entry also against the author DID’s deactivation at that time (P9.15, P5.18).

P7.10 A verifier MUST NOT report an Original that is not anchored as current, or its author or editors as currently authorized, however recently it obtained the asset log or the signers’ DID histories. Off Bitcoin nothing shows that a newer entry or another branch does not exist (P7.6, P6.6). A verifier MUST instead report a valid unanchored Original as valid as of its verified checkpoint, stating that checkpoint, the latest versionId it relied on for each signer’s DID and when it obtained that history. Only an anchored Original’s state derived from its anchoring sat (P9.13) can be reported as current, under the adapter’s confirmation policy (P9.5).

### Carried logs (proposed)

An Original often travels as a single file: a photograph sent by email, a note in a shared folder, a JSON document in a repository. A carried log lets that file keep the resource’s own media type, so it opens and previews as usual, and also carry the Original’s asset log, so that whoever holds the file can tell which Original it is and verify its history (owner request, 9 November 2026). A carried log is not an evidence package. It carries the log only: the signers’ DID histories are obtained by resolving their DIDs, as for any other source of the log, and other versions’ bytes are not included.

P7.11 A carried file is the exact bytes of one resource version with the Original’s asset log, from genesis through a checkpoint, added in the carrier that section 14 assigns to that version’s `mediaType` (P14.14–P14.17). The version is the one named by the log’s last entry, and the file is a carried version of the Original only if removing the carrier leaves exactly that version’s bytes. Bytes that are also a version of another Original are a version of both; a carried log identifies one of them, not the only one. A carried file MUST NOT be described as an evidence package, and it makes no claim to be complete (P7.1).

P7.12 A reader MUST remove exactly the carrier’s bytes, as section 14 defines them, and MUST NOT decode, re-encode, normalize or reformat what remains (P4.3). It MUST verify the carried log under this profile (P3.5), check that the carrier is the one P14.14 assigns to the last entry’s `mediaType`, and check the remaining bytes against that entry’s descriptor. If the bytes do not match, the file is not a carried version: the reader MUST NOT report its bytes as verified, and MAY report the Original and checkpoint the log identifies, with the log’s own result reported separately. The same applies to a carrier that P14.14 does not recognise in its position, such as a JSON member that is not the root object’s last: a reader MAY use its log to identify the Original, never to verify the file’s bytes.

P7.13 A carried log carries no signer DID history. A reader MUST obtain each signer’s DID history as for any other source of the log: by resolving the DID, or from history it retained or was given, recording what it relied on (P5.3, P7.8). If it cannot, it MUST report identity evidence as incomplete, never as a pass and never by trusting the key alone (P5.6). Versions other than the carried one are unavailable content, not a failure (P7.4).

P7.14 A carried log is a prefix as of its last entry, however recently the file was written. For an Original that is not anchored it MUST be reported as valid as of that checkpoint, never current (P7.10). For an anchored Original it is one more source of entries: its state MUST still be derived from the anchoring sat (P9.13), and a carried log MUST NOT be preferred to it. Importing a carried log follows P7.5: it never replaces newer local history and a different branch is a conflict.

P7.15 A writer MUST write a carrier only for an accepted checkpoint, never for a draft (P6.3), and its last entry MUST name the version whose bytes the file holds. It MUST refuse when section 14 assigns that `mediaType` no carrier, or when the carrier cannot be added as section 14 requires, and offer the log separately instead. Before writing, it MUST tell the author what the file will disclose: the Original’s whole history, including earlier names, metadata and the signers’ DIDs (P8.3), and, for a JSON carrier, that the document’s data gains a member (P14.17).

P7.16 Adding, replacing or removing a carrier MUST NOT be treated as a change to the Original: the resource version is the same bytes with or without it, and no entry is signed for it (P9.2).

::: example Harbor notes, carried
Alice keeps her notes as Markdown. Version 3 is the bytes B3, and her checkpoint is entry 4, a metadata correction after it. The SDK writes `harbor.md` as B3 followed by an HTML comment holding entries 1 to 4. Any Markdown viewer shows the notes as before. Bob, offline, removes the comment, verifies entries 1 to 4 and finds that the rest is B3, version 3; author binding is incomplete until he can resolve Alice’s DID. Online, he resolves it and reports the Original as valid as of entry 4, never current. If Bob’s editor had changed every line ending, the remaining bytes would match no version: he could still tell it is Alice’s Original at entry 4, but not that the file is version 3.
:::

### Proposed verification report

Return separate results for history validity, author binding, identity evidence, resource availability and freshness/order policy. List unverifiable inscriptions, and publications waiting on them, as a separate result; a single acceptance check MUST NOT pass while any is listed unless it presents the list with its result (P9.15); for an Original that is not anchored, the result is valid as of a checkpoint, never current (P7.10). Include the verified checkpoint, profile, unresolved dependencies, missing items and failures. Avoid a single green “verified” result that conceals incomplete identity evidence or unavailable historical bytes. If the SDK offers a single acceptance check, its default policy must require every part of the report to pass except content availability and the list of unverifiable inscriptions and waiting publications. Content availability is reported separately: a verified log with unavailable bytes passes as a log, and an application that needs the content checks availability as well. The list is presented with the check’s result (P9.15).

::: example Harbor at dawn, packaged
For the photo example, a package through photo version 2 contains the genesis and update entries, Alice’s identity evidence, plus B1 and B2. If B1 is omitted, the reader may still verify supplied history and B2 where all proof evidence is present, but reports that historical photo version 1 bytes are unavailable. It cannot claim to be a complete package.
:::

## Evidence packages and fresh verification

### Retained behavior and new evidence

An evidence package preserves signed history and historical resource bytes so a fresh reader can reconstruct versions. It additionally needs the author identity evidence that binds each signing key to the author’s DID. A public key being present in an archive is not sufficient evidence that an identity authorized it.

An evidence package describes what it includes and what is unavailable. Complete and partial packages must be distinguishable. Offline verification is an intended capability of a complete package, but it depends on specifying portable identity evidence and any freshness or external-ordering requirement.

### Proposed package rules

P7.1 An evidence package MUST declare whether it is complete or partial. A complete package MUST include the VH evidence through the selected checkpoint, the identity evidence required to check each entry’s signer binding, for the author and for every editor that signed an entry, and the historical resource bytes referenced by that prefix. It MUST identify the Original, profile and target checkpoint unambiguously. Two things are never in a package, complete or not: the history of a did:btco signer, which is read from Bitcoin (P14.10), and an anchor. For an anchored Original a package is one more source of entries, as P7.14 states for any copy of the log.

P7.2 Packaging MUST preserve signed bytes or canonical signed representations as required by each proof format. Reformatting, normalization or changing an envelope discriminator MUST NOT be presented as preserving an existing signature.

P7.3 A reader MUST validate evidence before exposing derived state as verified. Verification MUST establish identifier/genesis binding, history continuity, log authority, author binding and state transitions, and MUST check the digest of every resource byte sequence it is given. Resource bytes are not needed for the log to verify; missing ones are reported as unavailable content (P7.4, P9.18). A private key MUST NOT be required for any read-only check.

P7.4 Missing bytes MUST produce an `availability` of `partial` or `none` (P7.18) identifying the affected resource version and checkpoint. Available bytes MUST still be checked. Missing proof or identity evidence MUST be reported separately from missing content; no missing item permits bypassing a signature or digest check.

P7.5 Import MUST NOT confer signing authority, trust unknown keys, or replace an existing history with a conflicting branch without explicit handling. Untrusted archive paths, sizes and compression MUST be bounded before extraction. Import MUST reject absolute paths, `..` segments, symbolic links and duplicate entries. Import MUST NOT replace a newer local history with an older prefix of it.

P7.6 Evidence from a truncated prefix MUST NOT be represented as the latest state. For an anchored Original, an unverifiable inscription does not stop the accepted state before it being current; the report labels that inscription `unverifiable` and any publications waiting on it `waiting` (P7.19, P9.15). A valid historical prefix and a current result are separate claims, and off Bitcoin only the first can be made (P7.10). For entries not inscribed on an anchoring sat, reports MUST label ordering `claimed` (P7.19), except that an anchoring publication shows the entries before it existed no later than its block (P9.16).

P7.7 A verifier MUST enforce profile-defined limits on history length, entry size, identity-history length, and the number of editor grants (P14.13). When a history exceeds a limit, the verifier reports the last valid prefix as VH requires, and MUST report `history` as `limit-exceeded` and MUST NOT report it as complete or current (P7.18).

P7.8 The verification report MUST state, for the author DID and each editor DID it relied on, the latest versionId used and whether its freshness was independently established. An Original that is not anchored is never reported as current or currently authorized (P7.10). For an entry inscribed on an anchoring sat, a verifier checks each signer only against the versions Bitcoin evidences before that entry’s inscription (P9.15, P9.33): the signer history inscribed on the anchoring sat for a did:vh or did:webvh signer, and the DID’s own sat for a did:btco signer. Chain order establishes their freshness for that entry, and the report MUST state the latest version it relied on and the inscription that carried it. A version known from anywhere else MUST NOT change whether such an entry is accepted; a verifier MAY report beside the result, as a warning, a newer version it has verified that removes the entry’s key or deactivates the DID. For an entry that is not inscribed on an anchoring sat, a verifier checks each did:vh or did:webvh signer against the newest version of that DID in the evidence set (P7.17), whether supplied with the log, obtained by resolution, or retained from earlier verification and supplied as such. It is not required to show that no newer version exists, and the report MUST state that version and when it was obtained. If the evidence set holds a newer version than the one a package or host supplies, the verifier MUST use the newer one. A did:vh or did:webvh signer’s freshness is independently established only if that DID’s own witnesses or watchers support its latest version (P9.8); for a log obtained without that support, the report MUST state freshness as `not-established` (P7.18), together with where the log was obtained, when, and its latest versionId. A verifier MUST NOT treat a did:webvh log fetched from a location as that identity’s latest unless its latest version’s `id` names that location; this does not apply to did:vh logs or to logs from an evidence package. A did:webvh log whose latest version names another location shows that the identity has moved: the verifier MUST still use every verified version in it, including any that removes a key, SHOULD look for the moved log as P5.14 describes, and MUST report freshness as not established until it finds it. A report shown to a person MUST say plainly that the verifier obtained that DID’s history from that place at that time, and that the DID may have a newer version, such as one that removes a key, which the verifier has not seen. did:btco signers are read from Bitcoin (P5.13). Verifiers SHOULD retain the highest verified versionId seen for each signer DID and each Original, and include it in the evidence set of later verifications (P7.17), and compare copies of both logs as VH describes.

P7.9 For an entry that is not inscribed on an anchoring sat, a verifier MUST label the entry's authority from the latest version of its signer's DID in the evidence set (P7.19): `current-key` if the signing key is under assertionMethod there and that version, and for an editor entry the author DID's latest version, is not deactivated; `key-removed-since` if that version no longer lists the key; `did-deactivated-since` if it, or for an editor entry the author DID's latest version, is deactivated (P6.5, P5.18). The last two say only that the entry may have been signed after the key was removed or the DID deactivated (section 5), not that it was; their effect on acceptance, and how a later author entry endorses them, are given by P7.20 and P7.22, and any result that includes such an entry MUST give its label. An entry inscribed on an anchoring sat is checked instead against its signer's DID state that Bitcoin evidences at its inscription, and an editor entry also against the author DID's deactivation in that state (P9.15, P9.33, P5.18).

P7.10 A verifier MUST NOT report an Original that is not anchored as current, or its author or editors as currently authorized, however recently it obtained the asset log or the signers’ DID histories. Off Bitcoin nothing shows that a newer entry or another branch does not exist (P7.6, P6.6). A verifier MUST instead report a valid unanchored Original with `state` `valid-as-of` its verified checkpoint (P7.18), stating that checkpoint, the latest versionId it relied on for each signer’s DID and when it obtained that history. Only an anchored Original’s state derived from its anchoring sat (P9.13) can be reported as current, under the adapter’s confirmation policy (P9.5).

### Carried logs (proposed)

An Original often travels as a single file: a photograph sent by email, a note in a shared folder, a JSON document in a repository. A carried log lets that file keep the resource’s own media type, so it opens and previews as usual, and also carry the Original’s asset log, so that whoever holds the file can find which Original it claims to be and, once the signers’ DIDs are resolved, verify its history. A carried log is not an evidence package. It carries the log only: the signers’ DID histories are obtained by resolving their DIDs, as for any other source of the log, and other versions’ bytes are not included.

P7.11 A carried file is the exact bytes of one resource version with the Original’s asset log, from genesis through a checkpoint, added in the carrier that section 14 assigns to that version’s `mediaType` (P14.14–P14.17). The version is the one named by the log’s last entry, and the file is a carried version of the Original only if removing the carrier leaves exactly that version’s bytes. Bytes that are also a version of another Original are a version of both; a carried log identifies one of them, not the only one. A carried file MUST NOT be described as an evidence package, and it makes no claim to be complete (P7.1). The Original a carried file names is identified by its `did:og`, the `id` of the carried entries, and the file is one source from which that DID resolves (P3.9); the file itself has no identifier of its own.

P7.12 A reader MUST remove exactly the carrier’s bytes, as section 14 defines them, and MUST NOT decode, re-encode, normalize or reformat what remains (P4.3). It MUST verify the carried log under this profile (P3.5), check that the carrier, including a text block’s comment syntax, is the one P14.14 assigns to the last entry’s `mediaType`, and check the remaining bytes against that entry’s descriptor. If the bytes do not match, the file is not a carried version: the reader MUST NOT report its bytes as verified, and MAY report that the file carries the log of the Original and checkpoint it names only if it also states that the file is not a version of that Original; the log’s own result is reported separately. The overall result for the file MUST then be a failure with an explicit reason, such as a file digest mismatch: proofs that verified MAY be shown as detail and MUST NOT turn the overall result into a pass. The remaining bytes are not passed into the log’s own verification. The same applies to a log found where section 14 defines no carrier, such as an `originalLog` member that is not the root object’s last (P14.17).

P7.13 A carried log carries no signer DID history, and its proofs name keys without containing them (P14.8). A reader MUST obtain each signer’s DID history as for any other source of the log: by resolving the DID, or from history it retained or was given, recording what it relied on (P5.3, P7.8). Resolution follows P8.5 and needs the caller’s opt-in: a reader MUST NOT resolve a DID merely because a file was opened, previewed or imported, because the log’s author chose the DIDs and can learn who resolves them. An opt-in applies to a single read: there is no standing opt-in, and each later read needs the caller’s opt-in again before any resolver request. Importing a carried file (P7.14) never counts as one: an offline import stays offline. Until a reader has the signers’ DID histories, the entries’ proofs are unchecked: the reader MUST label those entries `unchecked` and report `identity` as `incomplete` (P7.18, P7.19), MUST NOT report the log or the version as verified, and MAY report only that the entries chain from the genesis the identifier binds and that the remaining bytes match the last entry’s descriptor, which anyone can arrange without a key. It MUST NOT trust a key alone (P5.6). Versions other than the carried one are unavailable content, not a failure (P7.4).

P7.14 A carried log is a prefix as of its last entry, however recently the file was written. For an Original that is not anchored it MUST be reported as valid as of that checkpoint, never current (P7.10). For an anchored Original it is one more source of entries: its state MUST still be derived from its anchor (P9.13), and a carried log MUST NOT be preferred to it. A reader that cannot read the anchor MUST report missing evidence (P3.3, P9.17). It MAY report only the entries before the anchoring entry, with `state` `historical-checkpoint` as of the checkpoint before it and `claimed` ordering; the anchoring entry and every later entry MUST be labelled `unchecked` (P7.19, P9.12, P9.15), and `bitcoin` reported as `missing-evidence`. A carried log that holds no anchoring entry is a historical checkpoint: it is reported with `state` `valid-as-of` that checkpoint, and the reader makes no statement about whether the Original has been anchored since. Importing a carried log follows P7.5: it never replaces newer local history and a different branch is a conflict. What this rule says of an anchored Original applies to every copy of its log that is not read from the anchor, including the log in an evidence package (P7.1): the state is derived from the anchor, the copy is not preferred to it, and a reader that cannot read the anchor reports missing evidence and at most the entries before the first anchoring entry.

P7.15 A writer MUST write a carrier only for an accepted checkpoint, never for a draft (P6.3); after anchoring, an entry not accepted on the anchoring sat (P9.12) is not one. A checkpoint from before an Original’s anchoring entry MAY still be carried after the Original is anchored, with no anchor evidence; a reader reports it as a historical checkpoint (P7.14). Its last entry MUST name the version whose bytes the file holds. A writer MUST refuse when section 14 assigns that `mediaType` no carrier, or when the carrier cannot be added as section 14 requires, and offer the log separately instead. Before writing, it MUST tell the user what the file will disclose: the Original’s whole history, including earlier names, metadata and the signers’ DIDs (P8.3); and, for a JSON carrier, that the document’s data gains a member (P14.17).

P7.16 Adding, replacing or removing a carrier MUST NOT be treated as a change to the Original: the resource version is the same bytes with or without it, and no entry is signed for it (P9.2). A carrier is therefore never part of what is published. When an inscription’s body is the version, it is the version’s bytes without a carrier (P9.17), and a writer MUST remove the carrier before inscribing a carried file’s bytes: with the carrier they do not match the descriptor, and the inscription is rejected. In the other direction, the body and entries of an accepted inscription whose body is the version are the two parts of a carried file, and a writer MAY make one from them under P7.15. A preview (P9.30) is not a resource version: it never has a carrier, and a writer MUST NOT make a carried file from it.

::: example Harbor notes, carried
Alice keeps her notes as Markdown. Version 3 is the bytes B3, and her checkpoint is entry 4, a metadata correction after it. The SDK writes `harbor.md` as B3 followed by an HTML comment holding entries 1 to 4. Any Markdown viewer shows the notes as before. Bob, offline, removes the comment and finds that entries 1 to 4 chain and that the rest is B3, but he cannot check their signatures, so nothing is verified yet: anyone could have written that log. Online, he resolves Alice’s DID, checks every proof, and reports the Original as valid as of entry 4, never current, with the file as version 3. If Bob’s editor had changed every line ending, the remaining bytes would match no version: he could report that the file carries the log of Alice’s Original at entry 4, but that it is not a version of it.
:::

### Verification result

A verification result is data, not prose. The rules below define what a verifier is given, what it reports and how a single acceptance check is decided, so that two verifiers given the same evidence report the same thing. Every result label this profile uses is defined here; other sections use these labels and cite these rules.

P7.17 Verification is a function of a declared [[ref: evidence set]], and of nothing else. The evidence set is: the Original's `did:og` and, if the caller names one, a target checkpoint; each copy of the log supplied, with its source (an evidence package and its manifest, a host, a carried file, the verifier's own storage); the resource and preview bytes supplied; each signer DID history supplied, with its source and the time it was obtained; for Bitcoin, the network, a tip (block hash and height), the confirmation depth the caller requires (P9.5), and what the index read at that tip (P9.31): the complete list of inscriptions on the anchoring sat and on each did:btco signer's sat that the verifier read, with their holders, and, if one is used, an index of Originals inscriptions with the block through which it is trusted (P9.16); and, optionally, a prior result for the same Original. Anything a verifier retains from earlier verification, such as a newer signer DID version (P7.8) or a head it reported before (P6.6, P9.15), affects a result only by being in the evidence set, as supplied history or as the prior result. A verifier MUST produce the same report for the same evidence set and MUST NOT let wall-clock time, network access during verification, cache state or the order in which inputs arrive change it. A report MUST identify its evidence set: the source and digest of each input, and the network and tip. A verifier that fetches more evidence produces a new report over a larger evidence set.

P7.18 A report gives one value for each of these axes, from the closed list for that axis, and a verifier MUST NOT report any other value or leave an applicable axis out:

| Axis | Values | Meaning |
|---|---|---|
| `outcome` | `verified`, `incomplete`, `invalid`, `unsupported` | `unsupported`: the profile or method value is not one the verifier implements (P3.3). `invalid`: `history` is `invalid`, or `binding` is `unbound`, or `identity` is `failed`. `incomplete`: none of these, but `identity` is `incomplete` or `bitcoin` is `missing-evidence` or `undetermined`. `verified`: otherwise. |
| `binding` | `bound`, `unbound` | Whether the genesis entry and SCID bind the `did:og` (P3.1–P3.5). |
| `history` | `valid`, `limit-exceeded`, `invalid` | Whether the entries through the reported checkpoint chain and transition validly; `limit-exceeded` as P7.7 states. |
| `identity` | `complete`, `incomplete`, `failed` | Whether every entry's signer binding was checked: `incomplete` when an entry is `unchecked` (P7.19) or a signer history is missing (P5.6); `failed` when a check failed. |
| `authority` | `current`, `historical` | `historical` when any entry through the checkpoint is labelled `key-removed-since` or `did-deactivated-since` and is not `endorsed` (P7.19, P7.20); `current` otherwise. |
| `state` | `current`, `valid-as-of`, `historical-checkpoint`, `conflict`, `none` | `current`: an anchored Original's state derived from its anchoring sat (P9.13), at the reported tip and depth. `valid-as-of`: an Original that is not anchored, valid as of the reported checkpoint (P7.10). `historical-checkpoint`: the entries before the anchoring entry, from a copy of a log that holds an anchoring entry, read without the anchor (P7.14); a copy with no anchoring entry is `valid-as-of` its last entry. `conflict`: divergent valid branches that nothing has settled (P6.6, P6.9); no branch's state is reported as the Original's. `none`: no valid entry. |
| `availability` | `complete`, `partial`, `none` | Whether the bytes of every resource version through the checkpoint were supplied and matched; `partial` and `none` list the missing versions (P7.4). |
| `offline` | `self-contained`, `needs-external` | Whether the result could be reproduced from the supplied package or file alone (P7.21). |
| `bitcoin` | `not-anchored`, `anchored`, `undetermined`, `missing-evidence`, `not-read` | `anchored`: an anchor was found (P9.16). `undetermined`: as P9.16 states. `missing-evidence`: the log names an anchor, or the caller asked for Bitcoin, and the anchoring sat could not be read in full (P3.3, P9.17). `not-read`: the evidence set has no Bitcoin input and nothing in the log names an anchor. `not-anchored`: Bitcoin was read and no anchor exists. |

For `bitcoin` `anchored`, the report also gives the anchoring sat, the holder as `provisional` or `established-through` a block (P9.11, P9.16), every conflicting anchor (P9.16), and each inscription labelled `unverifiable` or `waiting` (P9.15). For each signer DID relied on, it gives the latest version used, its source, and freshness as `established` or `not-established` (P7.8). For each missing or failed item, it gives a reason.

P7.19 A report labels each entry it considered with exactly one status and, for an accepted entry, its authority and ordering:

- Status: `accepted`; `rejected`, with the rule it fails; `unchecked`, when a proof could not be checked because the signer's DID history or the anchor needed to judge it is not in the evidence set (P7.13, P7.14); `unverifiable` and `waiting`, which apply only to inscriptions on the anchoring sat (P9.15); `ignored`, for a copy's entry after anchoring that is not inscribed on the sat, or an inscription that does not extend the head (P9.12, P9.13); and `conflicting`, for an entry on a branch that loses to an anchor or that an author entry has superseded (P6.9, P9.16).
- Authority, for an accepted entry: `current-key` when its signing key is under assertionMethod in the latest version of its signer's DID in the evidence set and that version is not deactivated, and for an editor entry the author DID's latest version is not deactivated either; `key-removed-since` when that latest version no longer lists the key; `did-deactivated-since` when that latest version, or for an editor entry the author DID's, is deactivated. An entry inscribed on the anchoring sat is judged under P9.15 instead and is always `current-key` if accepted. An accepted entry is also `endorsed` or not (P7.20).
- Ordering: `claimed` for an entry not inscribed on an anchoring sat (P7.6); `existed-by-block` for an entry before the anchoring entry in the anchoring publication, with that block (P9.16); `chain-ordered` for the anchoring entry and later inscribed entries (P9.13).

P7.20 An accepted entry is [[ref: endorsed]] when a later author entry on the same branch is accepted and labelled `current-key`: that entry's author, with a key the author DID lists now, has signed a state descending from it. An entry labelled `current-key` needs no endorsement. Under the default policy (P7.22) an entry labelled `key-removed-since` passes only if endorsed, because it may have been signed after the key was removed (section 5), and an entry labelled `did-deactivated-since` never passes, because no later author entry can be `current-key` once the author DID is deactivated; that Original's off-Bitcoin history stays reported but fails the default acceptance check. A host MAY accept a new entry extending an entry that is neither `current-key` nor endorsed only if the new entry is an author entry that is itself `current-key`, which endorses it; it MUST NOT accept an editor entry there. When an author removes a key they no longer hold (P5.9), the SDK SHOULD tell the author which unanchored entries the removal leaves unendorsed and offer to sign an author entry that endorses them.

P7.21 The `offline` axis is computed over the supplied package or carried file, whatever network access the verifier had. It is `self-contained` only when the package is complete (P7.1), includes the history of every did:vh and did:webvh signer it names, has no did:btco signer, and its log has no anchoring entry. Otherwise it is `needs-external`, and the report MUST list each external dependency: each did:btco signer's sat, the anchoring sat, and each signer DID whose history the package lacks. A never-anchored Original with a did:btco author therefore has a complete package that is not `self-contained`. A verifier given a `self-contained` package and no network MUST reach `outcome` `verified` if any verifier can from that package (P8.5).

P7.22 A single acceptance check, if a verifier or SDK offers one, uses this default policy unless the caller names another: it passes exactly when `outcome` is `verified`, `history` is `valid`, `authority` is `current`, and `state` is `current` or `valid-as-of`. It does not depend on `availability`, `offline` or the holder's uniqueness: content availability is reported separately, and an application that needs the content checks it as well. Each `unverifiable` or `waiting` inscription does not fail it, but MUST be presented with its result (P9.15). A *transfer check*, for a buyer or recipient of the anchoring sat, passes exactly when the default check passes, `bitcoin` is `anchored`, no inscription is `unverifiable` or `waiting`, and no conflicting anchor is reported; it reports the holder's uniqueness as given in the report. An application MUST NOT present any check as a single green "verified" that hides an axis it did not require.

P7.23 Every label in P7.18–P7.20 is the only form a verifier uses for that result: a verifier MUST NOT report the same condition under another name. The labels that other rules use map to these: "valid as of a checkpoint" to `state` `valid-as-of`; "current" to `state` `current`; "historically authorized" to `authority` `historical` with the entry labels of P7.19; "unresolved conflict" to `state` `conflict`; "conflicting anchor" to the list in P7.18; "incomplete identity evidence" to `identity` `incomplete`; "missing evidence" to `outcome` `incomplete` with `bitcoin` `missing-evidence` or a missing signer history; "unavailable content" and "partial availability" to `availability` `partial` or `none`; "claimed ordering" to `claimed`; "proofs unchecked" and "not checked against the anchor" to `unchecked`; "anchor undetermined" to `bitcoin` `undetermined`; "freshness not established" to `not-established`; "holder provisional" to `provisional`. The writer's labels "pending Bitcoin acceptance" and "submitted, not observed" (P9.18) describe a writer's own submission and are not verification results.

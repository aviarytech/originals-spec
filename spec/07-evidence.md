## Evidence packages and fresh verification

### Retained behavior and new evidence

An evidence package preserves signed history and historical resource bytes so a fresh reader can reconstruct versions. It additionally needs the author identity evidence that binds each signing key to the author’s DID. A public key being present in an archive is not sufficient evidence that an identity authorized it.

An evidence package describes what it includes and what is unavailable. Complete and partial packages must be distinguishable. Offline verification is an intended capability of a complete package, but it depends on specifying portable identity evidence and any freshness or external-ordering requirement.

### Proposed package rules

P7.1 An evidence package MUST declare whether it is complete or partial. A complete package MUST include the VH evidence through the selected checkpoint, the identity evidence required to check each entry’s signer binding, for the author and for every editor that signed an entry, and the historical resource bytes referenced by that prefix. It MUST identify the Original, profile and target checkpoint unambiguously. Two things are never in a package, complete or not: the history of a did:btco signer, which is read from Bitcoin (P14.10), and an anchor. For an anchored Original a package is one more source of entries, as P7.14 states for any copy of the log.

P7.2 Packaging MUST preserve signed bytes or canonical signed representations as required by each proof format. Reformatting, normalization or changing an envelope discriminator MUST NOT be presented as preserving an existing signature.

P7.3 A reader MUST validate evidence before exposing derived state as verified. Verification MUST establish identifier/genesis binding, history continuity, log authority, author binding and state transitions, and MUST check the digest of every resource byte sequence it is given. Resource bytes are not needed for the log to verify; missing ones are reported as unavailable content (P7.4, P9.18). A private key MUST NOT be required for any read-only check.

P7.4 Missing bytes MUST produce an explicit partial-availability result identifying the affected resource version and checkpoint. Available bytes MUST still be checked. Missing proof or identity evidence MUST be reported separately from missing content; no missing item permits bypassing a signature or digest check.

P7.5 Import MUST NOT confer signing authority, trust unknown keys, or replace an existing history with a conflicting branch without explicit handling. Untrusted archive paths, sizes and compression MUST be bounded before extraction. Import MUST reject absolute paths, `..` segments, symbolic links and duplicate entries. Import MUST NOT replace a newer local history with an older prefix of it.

P7.6 Evidence from a truncated prefix MUST NOT be represented as the latest state. For an anchored Original, an unverifiable inscription does not stop the accepted state before it being current; the report lists that inscription and any publications waiting on it (P9.15). A valid historical prefix and a current result are separate claims, and off Bitcoin only the first can be made (P7.10). For entries not inscribed on an anchoring sat, reports MUST label time and ordering as claimed only, except that an anchoring inscription shows the entries before it existed no later than its block (P9.16).

P7.7 A verifier MUST enforce profile-defined limits on history length, entry size, identity-history length and the number of editor grants. When a history exceeds a limit, the verifier reports the last valid prefix as VH requires, and MUST label the result limit-exceeded and MUST NOT report it as complete or current.

P7.8 The verification report MUST state, for the author DID and each editor DID it relied on, the latest versionId used and whether its freshness was independently established. An Original that is not anchored is never reported as current or currently authorized (P7.10). For an anchored Original, a verifier checks each did:vh or did:webvh signer against the newest version of that DID it knows of: the newest it has obtained from any source or retained from earlier verification (owner decision, 21 October 2026). It is not required to show that no newer version exists, and the report MUST state that version and when it was obtained. A verifier that knows of a newer version than the one a package or host supplies MUST use the newer one. A did:vh or did:webvh signer’s freshness is independently established only if that DID’s own witnesses or watchers support its latest version (P9.8); for a log obtained without that support, the report MUST state freshness as not established, together with where the log was obtained, when, and its latest versionId (owner decision, 23 October 2026). A verifier MUST NOT treat a did:webvh log fetched from a location as that identity’s latest unless its latest version’s `id` names that location; this does not apply to did:vh logs or to logs from an evidence package. A did:webvh log whose latest version names another location shows that the identity has moved: the verifier MUST still use every verified version in it, including any that removes a key, SHOULD look for the moved log as P5.14 describes, and MUST report freshness as not established until it finds it. A report shown to a person MUST say plainly that the verifier obtained that DID’s history from that place at that time, and that the DID may have a newer version, such as one that removes a key, which the verifier has not seen. did:btco signers are read from Bitcoin (P5.13). Verifiers SHOULD retain the highest verified versionId seen for each author DID and each Original, and compare copies of both logs as VH describes.

P7.9 If the signing key of an entry that is not inscribed on an anchoring sat is not under assertionMethod in the latest verified state of its signer’s DID, or the author DID’s latest verified state is deactivated (P6.5, P5.18), a verifier MUST report that entry as historically authorized only, because it may have been signed after the key was removed or the DID deactivated (section 5), and any result that includes it MUST say so. An entry inscribed on an anchoring sat is checked instead against its signer’s DID state at its inscription time, and an editor entry also against the author DID’s deactivation at that time (P9.15, P5.18).

P7.10 A verifier MUST NOT report an Original that is not anchored as current, or its author or editors as currently authorized, however recently it obtained the asset log or the signers’ DID histories. Off Bitcoin nothing shows that a newer entry or another branch does not exist (P7.6, P6.6). A verifier MUST instead report a valid unanchored Original as valid as of its verified checkpoint, stating that checkpoint, the latest versionId it relied on for each signer’s DID and when it obtained that history. Only an anchored Original’s state derived from its anchoring sat (P9.13) can be reported as current, under the adapter’s confirmation policy (P9.5).

### Carried logs (proposed)

An Original often travels as a single file: a photograph sent by email, a note in a shared folder, a JSON document in a repository. A carried log lets that file keep the resource’s own media type, so it opens and previews as usual, and also carry the Original’s asset log, so that whoever holds the file can find which Original it claims to be and, once the signers’ DIDs are resolved, verify its history (owner request, 9 November 2026). A carried log is not an evidence package. It carries the log only: the signers’ DID histories are obtained by resolving their DIDs, as for any other source of the log, and other versions’ bytes are not included.

P7.11 A carried file is the exact bytes of one resource version with the Original’s asset log, from genesis through a checkpoint, added in the carrier that section 14 assigns to that version’s `mediaType` (P14.14–P14.17). The version is the one named by the log’s last entry, and the file is a carried version of the Original only if removing the carrier leaves exactly that version’s bytes. Bytes that are also a version of another Original are a version of both; a carried log identifies one of them, not the only one. A carried file MUST NOT be described as an evidence package, and it makes no claim to be complete (P7.1). The Original a carried file names is identified by its did:vh, the `id` of the carried entries, and the file is one source from which that DID resolves (P3.9); the file itself has no identifier of its own.

P7.12 A reader MUST remove exactly the carrier’s bytes, as section 14 defines them, and MUST NOT decode, re-encode, normalize or reformat what remains (P4.3). It MUST verify the carried log under this profile (P3.5), check that the carrier, including a text block’s comment syntax, is the one P14.14 assigns to the last entry’s `mediaType`, and check the remaining bytes against that entry’s descriptor. If the bytes do not match, the file is not a carried version: the reader MUST NOT report its bytes as verified, and MAY report that the file carries the log of the Original and checkpoint it names only if it also states that the file is not a version of that Original; the log’s own result is reported separately. The overall result for the file MUST then be a failure with an explicit reason, such as a file digest mismatch: proofs that verified MAY be shown as detail and MUST NOT turn the overall result into a pass. The remaining bytes are not passed into the log’s own verification. The same applies to a log found where section 14 defines no carrier, such as an `originalLog` member that is not the root object’s last (P14.17).

P7.13 A carried log carries no signer DID history, and its proofs name keys without containing them (P14.8). A reader MUST obtain each signer’s DID history as for any other source of the log: by resolving the DID, or from history it retained or was given, recording what it relied on (P5.3, P7.8). Resolution follows P8.5 and needs the caller’s opt-in: a reader MUST NOT resolve a DID merely because a file was opened, previewed or imported, because the log’s author chose the DIDs and can learn who resolves them. Importing a carried file (P7.14) is not that opt-in: an offline import stays offline, and later reads of the imported Original need the caller’s separate opt-in before any resolver request. Until a reader has the signers’ DID histories, the entries’ proofs are unchecked: the reader MUST report identity evidence and author binding as incomplete, MUST NOT report the log or the version as verified, and MAY report only that the entries chain from the genesis the identifier binds and that the remaining bytes match the last entry’s descriptor, which anyone can arrange without a key. It MUST NOT trust a key alone (P5.6). Versions other than the carried one are unavailable content, not a failure (P7.4).

P7.14 A carried log is a prefix as of its last entry, however recently the file was written. For an Original that is not anchored it MUST be reported as valid as of that checkpoint, never current (P7.10). For an anchored Original it is one more source of entries: its state MUST still be derived from its anchor (P9.13), and a carried log MUST NOT be preferred to it. A reader that cannot read the anchor MUST report missing evidence (P3.3, P9.17). It MAY report only the entries before the anchoring entry, as valid as of the checkpoint before it with claimed ordering; the anchoring entry and every later entry MUST be reported as not checked against the anchor (P9.12, P9.15). This holds on whichever chain the anchor is (P9.20). For an Original whose carried log has an `anchor` member and an anchoring entry, the anchor is its token, read as P9.21–P9.25 require, and the report states the chain and its trust class (P9.27); with or without an anchoring entry, a reader whose revision of section 14 does not list that chain, or pins no anchor contract, MUST report the Original as unsupported, not invalid, and nothing as verified (P9.19, P14.21). For an Original whose carried log holds a move entry, the reader needs the chain the Original is anchored on now, and without it the entries it MAY report are those before the first anchoring entry. A chain the Original left that cannot be read is reported as P9.29 requires: the reader checks the log’s proofs and hash links from genesis, reports the move as unconfirmed, and MUST NOT report the ordering of the entries accepted on that chain as more than claimed. A carried log that holds no anchoring entry is a historical checkpoint: it is reported as valid as of that checkpoint, and the reader makes no statement about whether the Original has been anchored since, even when an `anchor` member would let it derive the token (P7.15). Importing a carried log follows P7.5: it never replaces newer local history and a different branch is a conflict. What this rule says of an anchored Original applies to every copy of its log that is not read from the anchor, including the log in an evidence package (P7.1): the state is derived from the anchor, the copy is not preferred to it, and a reader that cannot read the anchor reports missing evidence and at most the entries before the first anchoring entry.

P7.15 A writer MUST write a carrier only for an accepted checkpoint, never for a draft (P6.3); after anchoring, an entry not accepted on the anchor (P9.12) is not one, on Bitcoin or on an EVM chain at its finalized block (P9.22). A checkpoint from before an Original’s anchoring entry MAY still be carried after the Original is anchored, with no anchor evidence; a reader reports it as a historical checkpoint (P7.14). Its last entry MUST name the version whose bytes the file holds. A writer MUST refuse when section 14 assigns that `mediaType` no carrier, or when the carrier cannot be added as section 14 requires, and offer the log separately instead. Before writing, it MUST tell the user what the file will disclose: the Original’s whole history, including earlier names, metadata and the signers’ DIDs (P8.3); for a log with an `anchor` member, the chain and the minter’s address, which tie the Original to that account even before it is anchored (P14.18); and, for a JSON carrier, that the document’s data gains a member (P14.17).

P7.16 Adding, replacing or removing a carrier MUST NOT be treated as a change to the Original: the resource version is the same bytes with or without it, and no entry is signed for it (P9.2). A carrier is therefore never part of what is published. The body of an inscription or of an EVM publication is the version’s bytes without a carrier (P9.17, P9.25), and a writer MUST remove the carrier before inscribing or publishing a carried file’s bytes: with the carrier they do not match the descriptor, and the publication is rejected. In the other direction, the body and entries of accepted publications are the two parts of a carried file, and a writer MAY make one from them under P7.15.

::: example Harbor notes, carried
Alice keeps her notes as Markdown. Version 3 is the bytes B3, and her checkpoint is entry 4, a metadata correction after it. The SDK writes `harbor.md` as B3 followed by an HTML comment holding entries 1 to 4. Any Markdown viewer shows the notes as before. Bob, offline, removes the comment and finds that entries 1 to 4 chain and that the rest is B3, but he cannot check their signatures, so nothing is verified yet: anyone could have written that log. Online, he resolves Alice’s DID, checks every proof, and reports the Original as valid as of entry 4, never current, with the file as version 3. If Bob’s editor had changed every line ending, the remaining bytes would match no version: he could report that the file carries the log of Alice’s Original at entry 4, but that it is not a version of it.
:::

### Proposed verification report

Return separate results for history validity, author binding, identity evidence, resource availability and freshness/order policy. List unverifiable inscriptions, and publications waiting on them, as a separate result; a single acceptance check MUST NOT pass while any is listed unless it presents the list with its result (P9.15); for an Original that is not anchored, the result is valid as of a checkpoint, never current (P7.10). Include the verified checkpoint, profile, unresolved dependencies, missing items and failures. Avoid a single green “verified” result that conceals incomplete identity evidence or unavailable historical bytes. If the SDK offers a single acceptance check, its default policy must require every part of the report to pass except content availability and the list of unverifiable inscriptions and waiting publications. Content availability is reported separately: a verified log with unavailable bytes passes as a log, and an application that needs the content checks availability as well. The list is presented with the check’s result (P9.15).

::: example Harbor at dawn, packaged
For the photo example, a package through photo version 2 contains the genesis and update entries, Alice’s identity evidence, plus B1 and B2. If B1 is omitted, the reader may still verify supplied history and B2 where all proof evidence is present, but reports that historical photo version 1 bytes are unavailable. It cannot claim to be a complete package.
:::

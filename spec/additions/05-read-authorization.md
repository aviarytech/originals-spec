## Read authorization

Read authorization decides what a host serves, and to whom (owner decisions, 19 November 2026). Hosts enforce it; cryptography does not. It gives no confidentiality against the host itself, against anyone holding a copy, or against Bitcoin. It is not encryption (P8.2), which remains a later capability (D7). The author defines it in the asset state, next to the editor grants, and a host serving an Original checks it on every request. Reading and signing stay separate (P8.4): a read grant gives no authority to sign, and nothing in this section changes which entries verify. Writes are governed only by editor grants (P5.15–P5.18). In this section a *requester* is whoever asks a host for an Original; a reader in the sense of §7 of the core is the software that verifies what it receives.

P8.6 The asset state MAY carry a `readers` list of [[ref: read grants]] (member names provisional, D9). An Original whose state has no `readers` list is *public*, unless it is a child of a [[ref: parent Original]] (P8.10): any host MAY serve it to anyone, as hosts serve Originals today. An Original whose state has one, even an empty one, is *private*: the DIDs permitted to read it are the author DID, or for a [[ref: set Original]] each member of its signer set (P5.19, P5.30), each editor DID in `editors` and each DID in `readers`, together with those P8.10 adds. Each read grant names one DID. Each DID in `readers` MUST be unique in the list, MUST NOT be the author DID, a member of the signer set or an editor DID of the same state, MUST use a method that P5.8 lists, and MUST NOT be the Original’s did:og, any of its aliases or a did:btco DID whose sat is the Original’s anchoring sat. `readers` is not content that an editor grant covers (P5.15), so only an author entry can add, change or remove it (P5.16). A verifier MUST reject a state that breaks these rules, and MUST enforce the profile’s limit on the number of read grants (P14.13). An agent acting for a person reads under a grant to its own DID, which is a did:og for each agent, never under the person’s DID (owner decision, 19 November 2026).

P8.7 A host MUST NOT serve a private Original’s asset log or any of its entries, any resource version, a bundle or any part of one, a carried file, or any object that a profile names from the resource (P8.11), to a requester it has not authorized under P8.8 and P8.9. This applies to every route by which the host serves them, including the files that a did:webvh alias locates through `#files` (P14.11) and requests by digest. A request’s network, origin, referrer, identifier or digest alone MUST NOT authorize it. A host MAY serve the did:webvh alias log itself, which resolvers fetch without credentials (P8.5). That log shows that the Original exists and names its did:og, so an author who needs an Original’s existence kept private SHOULD NOT give it a did:webvh alias. A resolver or verifier that a host refuses MUST report missing evidence, not invalid evidence (P3.3).

P8.8 A host authorizes a requester against the newest verified state it holds for the Original: for an Original that is not anchored, the head of each valid branch it holds, and for an anchored Original, the state accepted on the anchor (P9.13). If it holds divergent branches (P6.6), it MUST authorize a requester only if every branch head it holds permits the requester, so that a revocation on any branch takes effect. A host MUST apply a revoking author entry from the moment it accepts that entry, including to sessions it issued earlier (P8.9). It MUST NOT authorize a requester from a state older than the newest verified state it holds, and MUST refuse every requester for a private Original of which it holds no verified state. This is an access decision, not a report: a host MUST NOT present its decision, or the grants it relied on, as showing that any grant is current (P7.10), and an author cannot rely on a revocation at a host that has not yet received the revoking entry. When a state makes a public Original private, P8.7 applies from then on; what the host served earlier is not withdrawn (P8.12).

P8.9 A requester proves that it controls a DID with a signed read request (P14.24). The request carries a Data Integrity proof with proof purpose `authentication`, made with a key that the DID’s `authentication` verification relationship lists. The proof’s `domain` is the host’s origin, its `challenge` is a single-use value that the host issued, and it expires no more than five minutes after it was created. A host MUST reject a read request whose domain is not its own origin, whose challenge it did not issue or has already accepted, that has expired, or whose key the `authentication` relationship of the newest version of the DID that the host holds does not list. The host obtains the DID’s history by resolving it under P8.5, from Bitcoin for a did:btco DID (P5.13), or from history the requester submits with the request. It MUST verify that history under the DID’s method, and MUST NOT accept a version older than the newest it has seen for that DID, as P5.8 requires for signers. It SHOULD refresh the DID’s history at each authentication; it MAY instead use history it refreshed within a freshness limit that it publishes. After accepting a read request, a host MAY issue its own session credential bound to that DID; P8.8 still applies to each request made with it. A session credential MUST NOT be one that a browser attaches automatically to requests to an origin that serves active content (P9.7).

P8.10 A child Original, one that names a [[ref: parent Original]] (P5.24), takes its read access from that parent. Its state MUST NOT carry `readers`, and a verifier MUST reject a state that does. It is public if the parent is public. Otherwise the DIDs permitted to read it are those permitted to read the parent, its own author DID or signer set members, and the editor DIDs in its own state. The parent still contributes editor grants only to authority to sign (P5.24): read access gives none (P8.4). For reads, a host checks the parent under P8.8, at the newest verified state of the parent that it holds, not at the [[ref: pin]] of any child entry. A parent’s revocation of a read grant therefore stops reads of every child at once, while a child editor entry that relied on a revoked [[ref: inherited grant]] stays valid and is reported as historically authorized only (P5.26). If the parent has a parent of its own, the host applies this rule to it in turn, within P14.13’s limit on nested parents. A host that holds no verified state of the parent MUST permit only the child’s own author or signer set members and its editors. A child’s evidence includes the parent’s log through the highest pin (P5.25). A host MAY serve that part of the parent’s log to a requester permitted to read the child, and serves the parent’s resource versions only to requesters permitted to read the parent. Read access to a child therefore discloses the parent’s log through the pin, with its names, metadata and grants.

P8.11 A host can store bytes once for several Originals and serve them by digest: resource versions, and objects that a profile names from a resource, such as the files of a version’s [[ref: path view]] (P5.29). A host MUST NOT serve such bytes to a requester unless the requester may read, under P8.6–P8.10, at least one Original whose verified history names that digest, as the digest of one of its versions or of an object that its profile names from one. A host MAY serve to anyone the digests that a public Original names. A host MUST answer a request it refuses under this rule exactly as it answers a request for a digest it does not hold, in status, headers and body, and SHOULD take the same time to do so. Otherwise a digest would act as a password, and a requester could learn whether a file whose bytes it can guess is present.

P8.12 Read authorization governs what a host serves, not what a copy discloses. Whoever holds a bundle, a carried file, an inscription or bytes that a host once served can read all of it, including earlier names, metadata, grants and signer DIDs, and for a child the parent’s log through its highest pin (P5.25), whatever a later state says (P8.3). Revoking a read grant, or making a public Original private, stops later service by hosts that apply it. It does not withdraw what was shared or served, and the SDK MUST NOT describe it as doing so. Before it writes a bundle or a carried file of a private Original for sharing, the SDK MUST tell the user, in addition to what P7.15 and P8.3 require, that whoever receives the file can read all of it and that no host’s read grants apply to it. A host serves a private Original’s bundles and carried files only under P8.7.

P8.13 Anchoring publishes on Bitcoin the whole log through the anchoring entry, every later inscribed entry and each inscription’s body (P9.17). From then on the log, including `readers` and `editors`, is public, and read authorization covers only bytes that no inscription carries, such as resource versions that were never inscribed (P9.18) and the objects that a profile names from them. Before it signs the anchoring entry of a private Original, the SDK MUST tell the author, in addition to what P9.18 requires, that the whole log, with every earlier name, metadata, grant and signer DID, becomes public permanently, which resource bytes the inscription’s body will make public, and that read grants will then cover only what Bitcoin does not hold. It MUST NOT sign the anchoring entry without the author’s explicit confirmation. Anchoring a parent Original publishes the parent’s log and grants, not the logs of its children.

P8.14 A read grant covers the whole Original (owner decision, 19 November 2026). Read scopes are left for later, and will use the [[ref: scope types]] of P5.28 and P5.29, such as a `paths` scope checked against a version’s path view. Until a profile defines read scopes, a verifier MUST reject a read grant that has a `scope` (P14.5). Once they are defined, a host that does not know a read grant’s scope type, or cannot apply it to the version requested, MUST treat that grant as permitting nothing. This is the reverse of P5.28, under which an unknown write scope leaves an entry unchecked, not rejected: an unchecked read scope fails closed.

### Hosted Originals

A host serves a public Original to anyone. For a private Original it applies the read rules of §8 of the core to every route by which it serves the log, the resources, bundles, carried files and objects by digest, and authorizes each request from the newest verified state it holds (P8.6–P8.11). Once an Original is anchored, those rules cover only what no inscription carries (P8.13).

### Read requests

P14.24 A read request (P8.9) is exactly `{type, did, proof}`, where `type` is `OriginalsReadRequest`, `did` is the requester’s DID and `proof` is a Data Integrity proof over the request without `proof`, canonicalized as P14.3 requires. The proof is exactly `{type, cryptosuite, proofPurpose, verificationMethod, created, expires, domain, challenge, proofValue}`:

- `type` is `DataIntegrityProof`, `cryptosuite` is `eddsa-jcs-2022` or `bip340-jcs-2025`, and `proofValue` is encoded as in P14.8;
- `proofPurpose` is `authentication`, and `verificationMethod` is the absolute id of a key that the `authentication` relationship of `did` lists;
- `created` and `expires` are UTC times in the form P14.2 requires of `versionTime`; `expires` MUST be later than `created` by at most five minutes, and a host MAY allow 60 seconds of clock difference when it compares them with its own clock;
- `domain` is the host’s origin, serialized as an ASCII origin such as `https://host.example`, with no path;
- `challenge` is the value the host issued, a string of at least 22 base64url characters encoding at least 128 random bits.

A host needs no particular transport. As a guide, a requester sends the base64url encoding of the request’s JCS form in an `Authorization` header with the scheme `OriginalsRead`, and a host issues challenges and session credentials at a location it publishes.

### Threats

| Adversary | Can | Cannot, under the baseline |
|---|---|---|
| Host that serves an Original | Serve a private Original to anyone, keep copies of it, or ignore a revocation: hosts enforce read authorization, and nothing else does (P8.6) | Change what verifies, or obtain an entry signature from a read request, whose proof purpose is `authentication` (P8.9) |
| Requester with no read grant | Learn that a private Original with a did:webvh alias exists, and its did:og (P8.7) | Read it at a host that applies §8 of the core; learn whether a host holds bytes whose digest it can guess (P8.11); replay a read request at another host or after it expires (P8.9) |
| Holder of a read grant, or of its key | Read what the grant covers, and keep or pass on copies, which no revocation withdraws (P8.12) | Sign entries, change grants or widen its own access (P8.6) |
| Holder of a revoked read grant | Keep what it fetched before; read at a host that has not yet received the revoking entry (P8.8) | Read at a host that holds the revoking entry, including with a session issued earlier (P8.8) |

## Signing and verification boundaries

Originals uses an identity signer and an independent verifier instead of an application-maintained device-key list such as the one planned for Boop [S11]. Each change has exactly one signature: the author, or an editor the author has granted, signs the VH entry with a verification method of their own DID. The author DID is the log’s controller, under VH-Log’s rule for authorized keys from a controller [S25], so the asset log has no updateKeys of its own and no rotation entries.

### Proposed rules for a signed change

P5.1 Each VH entry MUST carry, in its signed state, the Original identity, operation, resulting state commitment, resource transitions, the author DID, the absolute id of the author’s verification method and the exact author DID versionId; an editor entry also carries its editor reference (P5.16). The extension version is identified by the `method` parameter, and the VH entry chain binds the parent checkpoint. The VH proof MUST cover every security-relevant field, and only signed fields MAY affect verified state.

P5.2 An entry’s proof array MUST contain exactly one proof, and the signer binding MUST be evaluated against that proof’s key. The proof’s verificationMethod MUST be the absolute id of the signer’s verification method named in the signed state: the editor’s for an editor entry, otherwise the author’s.

P5.3 A verifier MUST check that the verification method named in the signed state is embedded in the author DID document at the named version, is listed under assertionMethod, is not an updateKey of the author DID’s own log at that version, has type Multikey, and has a publicKeyMultibase value that verifies the proof. Its id MUST be in the namespace of, and its controller MUST equal, that document’s `id`, which is the author DID or, after a did:webvh move, a DID that P5.14 relates to it. Verification methods held in another DID document, and a DID document’s controller property, MUST NOT confer authority.

P5.4 A verifier MUST reject an entry whose author binding fails, even when the VH proof is valid. A valid signature by any identity other than the Original’s author DID, or an editor whose grant in the parent’s state covers the change (P5.16), MUST NOT grant permission to change it.

P5.5 VH validation MUST apply the pinned upstream algorithms for entry integrity, chaining, parameters, proofs and controller changes.

P5.6 A candidate MUST NOT become the current state until the VH and author-binding checks succeed. Missing identity history MUST remain an explicit failure or incomplete-verification result; it MUST NOT downgrade to trusting the key alone.

P5.7 Parsers MUST reject duplicate keys, values that the pinned canonicalization cannot represent exactly, and any member of parameters, proof or Originals-defined state that is not defined by the pinned VH Log version, the pinned did:vh version or this extension.

P5.8 The author DID MUST be fixed at genesis; an entry naming a different author DID MUST be rejected. A did:webvh author that moves keeps this DID as its identity (P5.14). Authorship never transfers; selling an Original transfers ownership of its anchoring sat only (P9.11). Author DIDs MUST use a DID method with verifiable version history that the profile lists; the baseline profile lists did:vh, did:webvh and did:btco. The versionId an entry names for its signer MUST NOT be older than the one named by the most recent earlier entry signed by the same identity (for did:btco, by chain order, P5.13).

P5.9 The asset log’s controller is the author DID [S25]: an author entry is authorized by any key that meets P5.3 at the author DID version the entry names. An editor’s key authorizes only an editor entry, and only the change that the grant in the parent’s state allows (P5.16); it gives no other authority over the log. An entry that sets updateKeys or nextKeyHashes MUST be rejected. The author SHOULD remove from their DID any key they no longer hold. Deactivation is the only way to end an Original.

P5.10 Key rotation MUST happen only in the author DID. The asset log has no rotation entries: once the author DID adds a key, entries naming that DID version can be signed with it, and once it removes a key, Bitcoin readers refuse that key for an entry inscribed while the author DID’s state at the inscription does not list it (P9.15; for did:btco, P5.13), which for did:vh and did:webvh includes P9.15’s exception for a named later version that lists it again, and an unanchored entry signed with it is not current while the latest verified author DID state does not list it (P7.9).

P5.11 A signer holding an Originals key MUST parse the entry, show the person whose key signs it, the author for an author entry or the editor for an editor entry, the Original, operation and resource changes before signing, and refuse input that is not a well-formed Originals entry. The author’s Originals key SHOULD be used only for Originals entries; verifiers cannot check this, because any assertionMethod key of the author DID may sign the author’s Originals (P5.3). It MUST NOT also be an updateKey of the author DID’s own log, which P5.3 checks. For a did:btco author DID, the Originals key SHOULD NOT also be a key that can spend the output holding the DID’s sat; verifiers cannot check this.

P5.12 Each entry’s proof MUST use the `eddsa-jcs-2022` or `bip340-jcs-2025` cryptosuite, which the extension permits under VH-Log’s rule for additional cryptosuites [S21]. A verifier MUST reject any other cryptosuite.

P5.13 For a did:btco author DID, a version is an inscription on the DID’s sat that the did:btco method accepts as its DID document; an inscription is on the DID’s sat only if a Bitcoin index on the DID’s network reports it on the sat whose number the DID names (as for the anchoring sat, P9.10). Versions are ordered by [[ref: chain order]]. The DID document of each version is carried as CBOR metadata on its inscription, following the did:btco method v0.2.0 [S26], and the entry names a version by the versionId that method assigns it. A did:btco version exists only once it is inscribed, and its versionId can be known before then, because an inscription’s reveal can be prepared before it is broadcast. So for an anchored Original, the version an entry names MUST precede in chain order the inscription that carries the entry, or, for an entry before the anchor, the anchoring inscription; a verifier MUST reject an entry naming a version at or after that inscription, including one later in the same block. The author DID state at that inscription is the latest version that precedes it in chain order; P9.15 uses this instead of versionTime and timestamps. The named version is therefore never later than that state, and the key must meet P5.3 at both. did:btco versions are subject to the adapter’s confirmation policy (P9.5), and a deactivated version is terminal for this profile: later inscriptions on the DID’s sat MUST NOT be treated as versions. Whoever holds the DID’s sat controls the author DID: moving the sat moves control of the author DID, and with it the ability to change its assertionMethod keys and to sign as the author; the author DID named by each Original does not change (P5.8). A did:btco author DID’s sat MUST NOT be the anchoring sat of an Original naming that DID, and a verifier MUST reject an anchoring entry that names it.

P5.14 A signer’s identity is the DID that the signed state names for it: the author DID fixed at genesis (P5.8), or the editor DID in a grant (P5.15). The signed state names that DID, the absolute id of the verification method as it appears at the named version, and that version. A did:webvh can move to another host or path under the did:webvh method’s DID portability rules [S27], after which its DID document `id` changes while its SCID and log continue. A verifier MUST treat a version whose `id` differs from the identity DID as the same identity only if that version is in the identity DID’s own verified log, with the same SCID, reached through moves the did:webvh method accepts. P5.3 then compares the verification method with the `id` at the named version. Nothing else makes two DIDs one identity: not `alsoKnownAs`, an HTTP redirect, a host’s claim, a log with another SCID, or a log that does not verify from the identity DID’s genesis. did:vh and did:btco DIDs do not move, and a change of DID method is not continuity. Each entry binds to the version it names, so entries signed before a move keep verifying against versions from before it. A verifier finds each identity’s moved log in an evidence package, or at the location of the DID in the verification method id of the latest entry that identity signed, and MUST NOT follow redirects (P8.5). Editor entries carry the author reference unchanged from their parent, so they do not reveal where a moved author DID now is. When the verifier cannot obtain the identity’s log from an evidence package or the location named above, it MUST report that identity’s freshness as not established (P7.8), and MUST NOT report the Original as currently authorized. Freshness and revocation are judged on the identity’s whole log (P7.8, P7.9).

P5.15 The asset state MAY carry an `editors` list of grants (member names provisional, D4). Each grant names one editor DID and exactly which content that editor may change: `name` and `metadata`, each true or false, and `resources`, a list of resourceIDs from the Original’s resource set (P4.1). An absent list means no editors. Each editor DID MUST be unique in the list, MUST NOT be the author DID or, for a did:webvh author DID, a did:webvh with the same SCID, and MUST use a method that P5.8 lists. An editor DID MUST NOT be the Original’s did:vh, any of its aliases, or a did:btco DID whose sat is the Original’s anchoring sat, whether the grant is made before or after anchoring, so that holding the sat confers no edit authority (P9.12). A verifier MUST reject a state that breaks these rules, and MUST enforce the profile’s limit on the number of grants (P7.7).

P5.16 Every entry is an [[ref: author entry]] or an [[ref: editor entry]]. An author entry carries no editor reference and is signed by the author under P5.2 and P5.3. Only an author entry may change `editors`, aliases, lifecycle status or any parameter, and only an author entry may be the genesis entry, an anchoring entry (P9.10) or a deactivation (P6.5). An editor entry carries an editor reference in its signed state: the editor DID, the absolute id of the editor’s verification method and the exact editor DID versionId. The editor DID MUST have a grant in the parent entry’s state, and the signing key MUST meet P5.3 with the editor DID in place of the author DID. Its author reference MUST equal its parent’s. The author reference of an editor entry is checked only for equality with its parent’s; P5.3, P5.8 and P9.15 apply to it only through the author entry it was copied from. Its operation MUST be update and its parameters MUST be empty. Its state MUST equal its parent’s except for the name, metadata and resource descriptors its grant allows, the operation, the resource transitions and the editor reference. A verifier MUST reject an editor entry that breaks any of these rules, even when its proof is valid.

P5.17 A grant, a change to a grant and a revocation take effect from the entry after the author entry that makes them, because an editor entry is checked against the grants in its parent’s state. To revoke, the author appends an author entry whose `editors` list omits or narrows the grant. An editor entry whose parent’s state does not grant the change is rejected wherever it is published. An editor entry and a revoking author entry with the same parent are a fork (P6.6), not an ordering. If the fork exists before anchoring, it stays unresolved until the anchor settles it by carrying one branch (P6.6, P9.16). If both are offered on the anchoring sat after anchoring, the first in chain order that extends the accepted head is accepted and the other is ignored (P9.13). After anchoring, a revocation takes effect only once inscribed on the anchoring sat, which needs its holder (P9.12).

P5.18 The rules for the author’s keys apply to each editor’s keys with the editor DID in place of the author DID: P5.10 to P5.14, P7.8, P7.9 and P9.15, including P9.15’s exception for a later did:vh or did:webvh version that lists a removed key again. An editor rotates or removes keys, or moves, only in its own DID. An editor entry is also subject to the author DID’s deactivation exactly as an author entry is (P6.5, P9.15), so once the author DID is deactivated no editor can change the Original either. Editing is never identity administration: no entry can change the author DID or its keys, and an editor’s grant gives it none of the author’s keys.

### Key policy

The baseline profile has one author per Original, for the Original’s whole life, and any number of editors within the profile’s limit. The author’s DID is the Original’s controller [S25], and its own history, including any pre-rotation or, for did:btco, custody of its sat, protects its keys; pre-rotation does not apply to the asset log. VH-Log recommends pre-rotation for a log with an authoritative source [S20], so that the active keys alone cannot get an entry accepted. On Bitcoin that protection comes from the sat: an entry is accepted only if inscribed on the anchoring sat (P9.12). There is no per-Original keypair; one author key can sign for all of the author’s Originals. Naming the author DID in an entry grants no authority by itself; the key must also meet P5.3.

### Editors

The author grants each editor permission to change named content: the name, the metadata or particular resources. An editor signs its own entries with its own DID, and the author does not countersign them, so two editors can each make permitted changes while the author is offline. Every entry still names the author, and an editor entry also names the editor who made it.

An editor cannot change grants, so it cannot widen its own; it cannot add or change aliases, so it cannot publish to a new host or anchor; it cannot deactivate; and it holds none of the author DID’s keys. A grant names an editor DID, not keys, so the editor rotates its own keys in its own DID, and the author revokes the grant by an author entry. A fresh reader needs the asset log, which carries every grant and revocation, plus the history of the author DID and of each editor DID that signed an entry (P7.1).

::: example Harbor at dawn, edited by two editors
Alice grants Bob `resources: ["photo"]` and Carol `metadata: true`. Bob signs an entry replacing the photo, naming Alice as author and himself as editor. Carol, on the next head, signs an entry correcting the caption metadata. Neither entry is countersigned by Alice. An entry by Bob that renames the Original, or by Carol that changes the photo, is rejected. Later Alice signs an author entry removing Bob’s grant; Bob’s entries after it are rejected, and his earlier ones stay valid.
:::

### Key rotation and compromise

To rotate, the author updates their DID: they add the new key under assertionMethod and, if the old key is compromised, remove it in the same update. Nothing is appended to the asset logs.

For an unanchored Original, an entry signed with a removed key is never reported as current (P7.9), but nothing orders it: a thief holding the key before its removal can create a branch, which stays a reported fork until the Original is anchored (P6.6, P9.16).

For an anchored Original, Bitcoin readers check each inscribed entry against the author’s DID as it stood at the entry’s inscription time (P9.15). Removing a key refuses it for entries inscribed after the removal; entries already inscribed stay current, so rotating keys after selling an Original does not invalidate it.

These limits remain:

- Before the author removes the stolen key, the thief can edit or deactivate any Original the author controls; deactivation is permanent.
- A verifier that holds only stale author DID history does not see the removal (P7.8).
- For an unanchored Original, an entry signed with a removed key can name an older author DID version and cannot be distinguished from earlier entries. Verifiers report it as historically authorized with unproven ordering, never as current (P7.9).
- A lost key can be replaced by updating the author DID, as long as the author still controls the DID; recovering a lost DID is a separate decision (section 8).

Loading evidence does not restore signing authority, and claimed timestamps cannot establish signing before revocation.

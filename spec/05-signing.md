## Signing and verification boundaries

Originals uses an identity signer and an independent verifier instead of an application-maintained device-key list. Each signer signs the VH entry with a verification method of their own DID: the author, or an editor the author has granted. An Original MAY instead be governed by a [[ref: signer set]], a list of DIDs with a threshold, whose author entries carry one proof for each member who signs, and need at least the threshold (P5.19–P5.23, P5.30). An Original MAY also name a [[ref: parent Original]] whose editor grants it inherits, judged at a version each entry pins (P5.24–P5.27), and a grant MAY carry a scope that narrows the resource changes it allows (P5.28, P5.29). The author DID, or the signer set, is the log’s controller, under VH-Log’s rule for authorized keys from a controller [S25], so the asset log has no updateKeys of its own and no rotation entries.

An Original with no `authors` member is governed by its single author DID: the signer-set rules do not apply to it, and its entries, proofs and derived DID documents have the single-author form described below, so the signer-set rules change nothing in how it is written or verified.

### Proposed rules for a signed change

P5.1 Each VH entry MUST carry, in its signed state, the Original identity, operation, resulting state commitment, resource transitions, the author DID, the absolute id of the author’s verification method and the exact author DID versionId, or, for a [[ref: set Original]], such a reference for each member who signs (P5.19); an editor entry also carries its editor reference (P5.16). The extension version is identified by the `method` parameter, and the VH entry chain binds the parent checkpoint. The VH proof MUST cover every security-relevant field, and only signed fields MAY affect verified state.

P5.2 An entry’s proof array MUST contain exactly one proof for each signer reference in its signed state, in the order of those references (P5.22): for an editor entry, one proof, the editor’s; for an author entry of an Original without `authors`, one proof, the author’s; for an author entry of a set Original, one proof for each item of its `author` array. The signer binding of each proof MUST be evaluated against that proof’s key, and each proof’s verificationMethod MUST be the absolute id of the verification method named in its signer reference. For an Original without `authors` this is exactly one proof.

P5.3 A verifier MUST check, for each signer reference in the signed state, that the verification method it names is embedded in that signer’s DID document at the version it names, is listed under assertionMethod, is not an updateKey of that DID’s own log at that version, has type Multikey, and has a publicKeyMultibase value that verifies the proof that P5.2 pairs with that reference. Its id MUST be in the namespace of, and its controller MUST equal, that document’s `id`, which is the signer’s DID (the author DID, a member of the signer set, or the editor DID) or, after a did:webvh move, a DID that P5.14 relates to it. Verification methods held in another DID document, and a DID document’s controller property, MUST NOT confer authority, and a proof by one signer’s key MUST NOT count for another signer.

P5.4 A verifier MUST reject an entry whose author binding fails, even when the VH proof is valid. A valid signature by any identity other than the Original’s author DID, the members of its signer set signing as P5.20 requires, or an editor whose grant, in the parent’s state or inherited from a parent Original, covers the change (P5.16, P5.24), MUST NOT grant permission to change it.

P5.5 VH validation MUST apply the pinned upstream algorithms for entry integrity, chaining, parameters, proofs and controller changes.

P5.6 A candidate MUST NOT become the current state until the VH and author-binding checks succeed. Missing identity history MUST remain an explicit failure or incomplete-verification result; it MUST NOT downgrade to trusting the key alone.

P5.7 Parsers MUST reject duplicate keys, values that the pinned canonicalization cannot represent exactly, and any member of parameters, proof or Originals-defined state that is not defined by the pinned VH Log version, the pinned did:vh version or this extension.

P5.8 The author DID MUST be fixed at genesis; an entry naming a different author DID MUST be rejected. A did:webvh author that moves keeps this DID as its identity (P5.14). Authorship never transfers; selling an Original transfers ownership of its anchoring sat only (P9.11). Author DIDs MUST use a DID method with verifiable version history that the profile lists; the baseline profile lists did:vh, did:webvh and did:btco. The versionId an entry names for its signer MUST NOT be older than the one named by the most recent earlier entry signed by the same identity (for did:btco, by chain order, P5.13); for an entry with several signers this applies to each of them. For a set Original, the signer set is fixed in the same sense: it changes only by an author entry signed as P5.20 requires, and an Original without `authors` becomes a set Original only as P5.21 allows. No entry can make authorship pass by sale, by holding a sat or by paying for an inscription (P9.12).

P5.9 The asset log’s controller is the author DID [S25], or, for a set Original, its signer set: an author entry is authorized by any key that meets P5.3 at the author DID version the entry names, or, for a set Original, by the keys of the members P5.20 requires, each meeting P5.3 at the version its reference names. An editor’s key authorizes only an editor entry, and only the change that the grant in the parent’s state allows (P5.16); it gives no other authority over the log. An entry that sets updateKeys or nextKeyHashes MUST be rejected. The author SHOULD remove from their DID any key they no longer hold. Deactivation is the only way to end an Original.

P5.10 Key rotation MUST happen only in the author DID. The asset log has no rotation entries: once the author DID adds a key, entries naming that DID version can be signed with it, and once it removes a key, Bitcoin readers refuse that key for an entry inscribed while the author DID’s state at the inscription does not list it (P9.15; for did:btco, P5.13), which for did:vh and did:webvh includes P9.15’s exception for a named later version that lists it again, and an unanchored entry signed with it is not current while the latest verified author DID state does not list it (P7.9).

P5.11 A signer holding an Originals key MUST parse the entry, show the person whose key signs it, the author for an author entry or the editor for an editor entry, the Original, operation and resource changes before signing, and refuse input that is not a well-formed Originals entry. The author’s Originals key SHOULD be used only for Originals entries; verifiers cannot check this, because any assertionMethod key of the author DID may sign the author’s Originals (P5.3). It MUST NOT also be an updateKey of the author DID’s own log, which P5.3 checks. For a did:btco author DID, the Originals key SHOULD NOT also be a key that can spend the output holding the DID’s sat; verifiers cannot check this.

P5.12 Each entry’s proof MUST use the `eddsa-jcs-2022` or `bip340-jcs-2025` cryptosuite, which the extension permits under VH-Log’s rule for additional cryptosuites [S21]. A verifier MUST reject any other cryptosuite.

P5.13 For a did:btco author DID, a version is an inscription on the DID’s sat that the did:btco method accepts as its DID document; an inscription is on the DID’s sat only if a Bitcoin index on the DID’s network reports it on the sat whose number the DID names (as for the anchoring sat, P9.10). Versions are ordered by [[ref: chain order]]. The DID document of each version is carried as CBOR metadata on its inscription, following the did:btco method v0.2.0 [S26], and the entry names a version by the versionId that method assigns it. Whether an inscription is a version depends only on its own metadata: a body delegated to another inscription, or a content encoding, does not affect it. An inscription whose metadata is not a DID document for that DID is not a version. An inscription whose metadata the verifier has not read is missing evidence: the DID’s history ends before it, and an entry whose check depends on that history beyond it has incomplete identity evidence (P5.6) or, if inscribed after the anchoring inscription, is unverifiable (P9.15). If a later did:btco method version that this profile pins decides otherwise, that rule applies from that profile version. A did:btco version exists only once it is inscribed, and its versionId can be known before then, because an inscription’s reveal can be prepared before it is broadcast. So for an anchored Original, the version an entry names MUST precede in chain order the inscription that carries the entry, or, for an entry before the anchor, the anchoring inscription; a verifier MUST reject an entry naming a version at or after that inscription, including one later in the same block. The author DID state at that inscription is the latest version that precedes it in chain order; P9.15 uses this instead of versionTime and timestamps. The named version is therefore never later than that state, and the key must meet P5.3 at both. did:btco versions are subject to the adapter’s confirmation policy (P9.5), and a deactivated version is terminal for this profile: later inscriptions on the DID’s sat MUST NOT be treated as versions. Whoever holds the DID’s sat controls the author DID: moving the sat moves control of the author DID, and with it the ability to change its assertionMethod keys and to sign as the author; the author DID named by each Original does not change (P5.8). A did:btco author DID’s sat MUST NOT be the anchoring sat of an Original naming that DID, and a verifier MUST reject an anchoring entry that names it.

P5.14 A signer’s identity is the DID that the signed state names for it: the author DID fixed at genesis (P5.8), or the editor DID in a grant (P5.15). The signed state names that DID, the absolute id of the verification method as it appears at the named version, and that version. A did:webvh can move to another host or path under the did:webvh method’s DID portability rules [S27], after which its DID document `id` changes while its SCID and log continue. A verifier MUST treat a version whose `id` differs from the identity DID as the same identity only if that version is in the identity DID’s own verified log, with the same SCID, reached through moves the did:webvh method accepts. P5.3 then compares the verification method with the `id` at the named version. Nothing else makes two DIDs one identity: not `alsoKnownAs`, an HTTP redirect, a host’s claim, a log with another SCID, or a log that does not verify from the identity DID’s genesis. did:vh and did:btco DIDs do not move, and a change of DID method is not continuity. Each entry binds to the version it names, so entries signed before a move keep verifying against versions from before it. A verifier finds each identity’s moved log in an evidence package, or at the location of the DID in the verification method id of the latest entry that identity signed whose signer binding the verifier has verified, and MUST NOT follow redirects (P8.5). When it has verified none, it SHOULD ask first at the location named by the earliest entry that identity signed, in log order, which for the author is the genesis entry, and MAY then ask at the location named by the latest. When the location named by the latest verified entry does not give it a log newer than it holds, it MAY also ask at the location named by the latest entry that identity signed, verified or not. If a verified log obtained from any of these locations has a latest version whose `id` names another location, the verifier SHOULD ask at that location. A log obtained from any location MUST verify from the identity DID’s genesis, so an unverified entry can choose where a request goes but never what is accepted. Editor entries carry the author reference unchanged from their parent, so they do not reveal where a moved author DID now is. When the verifier cannot obtain the identity’s log from an evidence package or the location named above, it MUST report that identity’s log as not obtained, and freshness as not established (P7.8), and MUST NOT report the Original as currently authorized. Freshness and revocation are judged on the identity’s whole log (P7.8, P7.9).

P5.15 The asset state MAY carry an `editors` list of grants (member names provisional, D4). Each grant names one editor DID and exactly which content that editor may change: `name`, `metadata` and `resource`, each true or false, where `resource` allows new versions of the Original’s one resource (P4.1), and MAY carry a `scope` that narrows what `resource` allows (P5.28). An absent list means no editors. Each editor DID MUST be unique in the list, MUST NOT be the author DID or, for a did:webvh author DID, a did:webvh with the same SCID, MUST NOT be a member of the `authors` of the same state or, for a did:webvh member, a did:webvh with the same SCID, MUST NOT be the did:vh or an alias of the Original’s parent Original (P5.24), and MUST use a method that P5.8 lists. An editor DID MUST NOT be the Original’s did:vh, any of its aliases, or a did:btco DID whose sat is the Original’s anchoring sat, whether the grant is made before or after anchoring, so that holding the sat confers no edit authority (P9.12). A verifier MUST reject a state that breaks these rules, and MUST enforce the profile’s limit on the number of grants (P7.7).

P5.16 Every entry is an [[ref: author entry]] or an [[ref: editor entry]]. An author entry carries no editor reference and is signed by the author under P5.2 and P5.3, or, for a set Original, by members of its signer set under P5.20. Only an author entry may change `editors`, `authors`, aliases, lifecycle status or any parameter, and only an author entry may be the genesis entry, an anchoring entry (P9.10) or a deactivation (P6.5). No entry may change `parent.did`, and only the genesis entry may set `parent` (P5.24); an author entry or an editor entry MAY advance the pin `parent.versionId`, and advancing it is not a change the editor’s grant must allow. An editor entry carries an editor reference in its signed state: the editor DID, the absolute id of the editor’s verification method and the exact editor DID versionId. The editor DID MUST have a grant in the parent entry’s state, or an inherited grant from the parent Original at the version the entry pins (P5.24), and the signing key MUST meet P5.3 with the editor DID in place of the author DID. Its author reference MUST equal its parent’s; for a set Original that is the whole `author` array, unchanged. The author reference of an editor entry is checked only for equality with its parent’s; P5.3, P5.8 and P9.15 apply to it only through the author entry it was copied from. Its operation MUST be update and its parameters MUST be empty. Its state MUST equal its parent’s except for the name, metadata and resource descriptor its grant allows, within the grant’s scope if it has one (P5.28), the `preview` that goes with a new version under a grant that allows the resource (P9.30), the pin (P5.24), the operation, the resource transition and the editor reference. A verifier MUST reject an editor entry that breaks any of these rules, even when its proof is valid.

P5.17 A grant, a change to a grant and a revocation take effect from the entry after the author entry that makes them, because an editor entry is checked against the grants in its parent’s state. To revoke, the author appends an author entry whose `editors` list omits or narrows the grant. An editor entry whose parent’s state does not grant the change is rejected wherever it is published. An editor entry and a revoking author entry with the same parent are a fork (P6.6), not an ordering. If the fork exists before anchoring, it stays unresolved until the anchor settles it by carrying one branch (P6.6, P9.16). If both are offered on the anchoring sat after anchoring, the first in chain order that extends the accepted head is accepted and the other is ignored (P9.13); if the first is unverifiable, the other waits until it is resolved (P9.15). After anchoring, a revocation takes effect only once inscribed on the anchoring sat, which needs its holder (P9.12). A grant, change or revocation in a parent Original reaches a child entry through the version that entry pins (P5.24); P5.26 and P5.27 say how a revocation affects child entries pinning an earlier version.

P5.18 The rules for the author’s keys apply to each editor’s keys with the editor DID in place of the author DID: P5.10 to P5.14, P7.8, P7.9 and P9.15, including P9.15’s exception for a later did:vh or did:webvh version that lists a removed key again. An editor rotates or removes keys, or moves, only in its own DID. An editor entry is also subject to the author DID’s deactivation exactly as an author entry is (P6.5, P9.15), so once the author DID is deactivated no editor can change the Original either; for a set Original, P5.23 says when the signer set counts as deactivated. Editing is never identity administration: no entry can change the author DID or its keys, and an editor’s grant gives it none of the author’s keys.

### Signer sets

P5.19 A [[ref: set Original]] is an Original whose asset state has an `authors` member: a threshold and a list of member DIDs, the [[ref: signer set]], with a threshold of at least 1 and at most the number of members, and at most 32 members (P14.5, P14.13). Each member MUST use a method that P5.8 lists and MUST be unique in the list, and no two members may be one identity under P5.14: a list with two did:webvh members with the same SCID MUST be rejected. A member MUST NOT be the Original’s did:vh, any of its aliases, its parent Original’s did:vh or aliases (P5.24), or a did:btco DID whose sat is the Original’s anchoring sat, whether the member is added before or after anchoring (P5.13, P9.12). In every entry of a set Original, editor entries included, `author` is an array of signer references, each `{did, verificationMethod, versionId}` as P5.1 describes, sorted by `did` and unique (P14.4); in every entry of an Original without `authors` it is one signer reference, exactly as before. An entry’s `author` MUST be an array exactly when its state has `authors`. Once an entry has `authors`, every later entry MUST have it: a set MAY shrink to one member, and a set of one is still a set Original. The genesis entry of a set Original MUST be signed by every member: its `author` array names exactly the DIDs in `authors`, so that nobody becomes a member without signing. A verifier MUST reject a state or entry that breaks these rules.

P5.20 The [[ref: authorizing set]] of an author entry other than the genesis entry is the signer set of its parent entry’s state, with that state’s threshold; for a parent entry whose state has no `authors`, it is the author DID alone, with threshold 1. An author entry of a set Original MUST be signed by at least the authorizing set’s threshold of that set’s members. If the entry’s `authors` lists DIDs that the authorizing set does not, every member it adds MUST also sign it, and those signatures do not count toward the threshold. Every DID in the entry’s `author` array MUST be a member of the authorizing set or a member the entry adds. A verifier MUST reject an entry that names any other signer, even when that signer’s proof is valid, and an entry signed by fewer of the authorizing set’s members than its threshold. Removing members and changing the threshold need only the authorizing set’s threshold. This applies to every author entry of a set Original, including an anchoring entry (P9.10) and a deactivation (P6.5). Paying for, broadcasting or inscribing an entry confers no authority (P9.12).

P5.21 An author entry of an Original without `authors` MAY add `authors`, which makes the Original a set Original from that entry on. Its authorizing set is the author alone (P5.20), so the author signs it, and every other member signs it because the entry adds them. The new set MUST include the author DID, and a verifier MUST reject a conversion whose `authors` does not. The author DID named at genesis is then a member like any other, and the set changes only under P5.20.

P5.22 An entry’s proofs correspond one to one, in order, with its signer references: for an author entry of a set Original, the items of its `author` array, sorted by `did`; otherwise its one signer reference (P5.2, P14.8). Each proof’s `verificationMethod` MUST be byte-identical to its reference’s, and P5.3, P5.11 and P5.12 apply to each signer against its own DID. A verifier MUST reject an entry with a proof too many or too few, or with its proofs in another order. Every proof MUST verify: a verifier MUST NOT ignore an invalid proof because the others meet the threshold. The proofs form a set, not a chain: each covers the entry without any proof, so members can sign the same unsigned entry independently and in any order, and the proofs are then put in order.

P5.23 For an author entry of a set Original that is not inscribed on an anchoring sat, P7.9 counts signers: the entry MUST be reported as historically authorized only unless at least the authorizing set’s threshold of its signers that are members of that set (for the genesis entry, of its own set) pass P7.9’s test, their signing key being under assertionMethod in the latest verified state of their DID and that state not deactivated. An author entry of a set Original inscribed on the anchoring sat is checked under P9.15 for each signer at the inscription. Every signer MUST pass, which keeps the threshold there: an entry with a signer that fails is rejected, and one with a signer whose named version cannot be verified is unverifiable (PROVISIONAL). Where P5.18, P7.9 and P9.15 make an entry depend on the author DID not being deactivated, for a set Original the condition is that at least its threshold of members have a DID state that is not deactivated: in their latest verified state for P7.9, and at the inscription for P9.15. The set is the one in the entry’s parent entry’s state, which for an editor entry is also its own (PROVISIONAL).

### Parent Originals

P5.24 An Original MAY name a [[ref: parent Original]] in its asset state’s `parent` member: the parent’s did:vh, and a versionId of the parent’s asset log, the [[ref: pin]] (P14.5). Only the genesis entry may set `parent`. A verifier MUST reject a later entry that adds or removes it or changes `parent.did`, and an entry whose `parent.did` is the Original’s own did:vh. Each later entry’s pin MUST be its parent entry’s pin or a later version of the parent’s log that descends from it; a pin that goes backwards, or moves to another branch of the parent’s log, MUST be rejected. A child Original cannot leave its parent except by deactivation (P6.5). The parent contributes editor grants only: its author, its signer set, its editors and the holder of its anchoring sat have no authority over the child by those roles, and the child keeps its own author or signer set, fixed at genesis (P5.8). An editor entry of a child is authorized by a grant in its parent entry’s `editors` (P5.16), or by an [[ref: inherited grant]]: a grant in the `editors` of the parent Original’s state at the version that entry pins. An inherited grant’s `name`, `metadata`, `resource` and `scope` apply to the child’s content exactly as a direct grant’s would, and P5.16 and P5.18 apply to its editor as to any editor. The change MUST be allowed by one grant, direct or inherited, not by a combination of grants. Only the parent’s own `editors` are inherited: grants that the parent inherits from a parent of its own give the child nothing. An inherited grant whose DID the child’s own state could not grant under P5.15, such as the child’s author DID, a member of its signer set, the child’s did:vh or an alias, or a did:btco DID whose sat is the child’s anchoring sat, authorizes nothing. The report MUST state, for each editor entry, whether a direct or an inherited grant authorized it, and for an inherited grant the parent version it relied on; when a direct grant allows the change, the entry is reported as authorized by it.

P5.25 Checking an entry of a child Original needs the parent’s asset log through that entry’s pin, verified as an Original under this profile (P3.5), with its own signer evidence and, if the parent has a parent of its own, that parent’s evidence in turn, within P14.13’s limit on nested parents. Every entry’s pin is checked, not only those of entries that rely on an inherited grant. An evidence package for the child includes the parent’s log through the highest pin in the packaged prefix, with the evidence that the parent’s own check needs (P7.1, P14.10). A verifier without that evidence MUST report the child’s result as incomplete, with the parent evidence listed as missing, and never as a pass (P5.6, P7.4). The pin MUST name a version in the parent’s verified log. For a parent that is not anchored, a verifier that holds no version with the pinned versionId MUST report the child’s result as incomplete, with the pinned parent version listed as missing, even when it holds the parent’s log past that version number: the pin may name a version on a branch of the parent’s log that it has not obtained (P6.6), and missing evidence is never a rejection or a pass (P7.4). For an anchored parent, a pin that is not in the parent’s accepted history from its anchoring sat, up to the latest version the verifier holds, MUST be rejected, because entries not inscribed on that sat form no competing branch (P9.12, P9.13). A pin MAY name the parent’s deactivation, but the parent grants nothing at it: an editor entry that relies on an inherited grant there MUST be rejected.

P5.26 An editor entry of a child that only an inherited grant authorizes, and that P5.27 does not cover, MUST be reported as historically authorized only when the parent Original’s latest verified state does not grant the same change: the grant is absent or narrowed there, or that state is deactivated. A parent with divergent valid branches has no latest state (P6.6), so such entries are then historically authorized only. The entries stay valid, as entries signed with a key later removed do (P7.9); only their label changes. The parent’s later state does not affect a child entry that does not rely on an inherited grant. Until an entry of the child pins a parent version at or after a revocation, the revoked editor can still append entries pinning an earlier version; they too are historically authorized only.

P5.27 For the anchoring entry, and each later entry, of a child inscribed on the child’s anchoring sat at a point in chain order where the parent Original is anchored, the pin MUST NOT be older, in the parent’s accepted log, than the parent’s accepted head at the child entry’s inscription (P9.13): it MUST be that head or an entry that follows it in the parent’s accepted log. A verifier MUST reject an inscribed child entry that breaks this. To check it, the verifier reads the parent’s anchoring sat through the child’s inscription; while it cannot, or while the pinned entry is not yet accepted on the parent’s sat, the child’s inscription is unverifiable (P9.15), and once the parent’s accepted log can no longer contain the pinned entry, the child entry is rejected (PROVISIONAL). A verifier finds the parent’s anchoring sat through a did:btco alias in a parent state it holds; if it holds none, it reports the parent’s anchoring as not checked and applies P5.26. An unanchored child, and the child entries before its anchoring entry, have no ordering against the parent’s inscriptions, so only P5.26 applies to them.

### Scoped grants

P5.28 A grant’s `scope` (P14.5, P14.23) narrows what `resource: true` allows; it never widens a grant and never affects `name` or `metadata`. A grant that has `scope` and `resource: false` MUST be rejected. The scope’s `type` names a [[ref: scope type]], which defines its other members, the resources it applies to and how it is checked; this profile defines two (P5.29). A verifier MUST reject a scope of a type it knows whose members break that type’s rules. A scope of a type it does not know is not rejected, and every entry that relies on it is unchecked. A verifier checks the scope of the grant that an editor entry relies on whenever the entry changes the resource’s digest: the change from the version in the entry’s parent entry to the version the entry names MUST stay within the scope, and a verifier that finds it outside MUST reject the entry, even when its proof is valid. An editor entry that does not change the digest is not checked against the scope. A verifier that does not know the scope type, or cannot apply it to the media type of either version, or lacks bytes that the check needs, MUST report the entry’s scope as unchecked. The entry is then not verified as authorized: the result is incomplete, never a pass and never a rejection (P5.6, P7.4). An entry inscribed on an anchoring sat after the anchoring inscription whose scope is unchecked is unverifiable (P9.15) (PROVISIONAL). The report MUST state, for each entry that relies on a scoped grant, the scope type and whether it was checked, and for a rejection, the paths or items outside the scope.

P5.29 This profile defines two scope types, whose members and syntax are in section 14 (P14.23):

- `paths` applies to a resource media type that defines a [[ref: path view]]: a map from each path in a version to a digest of everything the media type records for that path, such as its content and file mode, computed from the version’s bytes and the objects they reference. The paths a change touches are those added, those removed and those whose digest changes, so a rename touches both its old and its new path. Every touched path MUST match at least one of the scope’s patterns.
- `items` applies to a resource media type that defines an [[ref: item view]]: a map from each item’s id to a digest of everything the media type records for that item. A new id is an add, an id that is gone is a remove, and an id whose digest changes is an edit. Every change MUST be of an operation that the scope lists.

A media type defines its path view or item view in its own specification. This profile defines none, so a verifier checks a `paths` or `items` scope only for media types whose view it implements (P5.28). For example, the Originals SDK’s provisional code tree media type, `application/vnd.originals.code-tree+json`, defines a path view, and a list media type can define an item view. If the two versions of a change have different media types, both MUST define the view, or the scope is unchecked (PROVISIONAL). Read grants are specified separately; they may later carry the same `scope`, and they are inherited through a parent Original as editor grants are (P5.24).

### Set Originals in other rules

P5.30 Elsewhere in this profile, a rule stated for an Original’s author or author DID reads, for a set Original, as follows. A check of the author’s signing key or DID history (P5.3, P5.10, P5.13, P5.14, P7.8, P9.15, P9.18) applies to each member who signs the entry, against that member’s DID. An entry signed by the author (P6.6, P9.10, P9.12, P9.16) is an author entry signed as P5.20 requires. The author’s identity evidence (P7.1, P7.8, P9.18) is that of every member that signed an entry, which is every member, because each signs its genesis or the entry that adds it. The author DID’s deactivation reads as P5.23 says. A signer holding a member’s key MUST also show the signer set, its threshold, any change to either, and the members who have already signed, before signing (P5.11). For an Original without `authors`, every rule reads as written.

::: example A repository with three delegates, and a branch
Alice, Bob and Carol govern a repository Original R as a signer set with threshold 2. R’s genesis entry names all three in its `author` array and carries three proofs, one from each, in DID order. Later Alice and Carol sign an author entry that grants Dana `resource: true` with the scope `{"type": "paths", "paths": ["docs/**"]}`; Bob’s proof is not needed. Bob alone cannot change R’s grants, anchor it or deactivate it, and neither can whoever pays for an inscription.

Bob’s branch Original B names R as its parent, pinning R at the version that grants Dana. B’s author is Bob alone, and R’s signer set has no authority over B. Dana signs an editor entry of B that changes `docs/guide.md`. No grant in B names Dana, but the grant inherited from R at B’s pin covers the change, and the report says so. An entry by Dana that also changes `src/main.ts` touches a path outside `docs/**` and is rejected; renaming `docs/a.md` to `src/a.md` touches both paths and is rejected too. A verifier that has no path view for B’s code tree media type reports Dana’s entries as unchecked, not valid. If Alice and Carol later remove Dana’s grant from R, Dana’s entries in B stay valid but are reported as historically authorized only. Once any entry of B pins R at or after the removal, Dana’s later entries in B are rejected.
:::

### Key policy

The baseline profile has one author per Original, for the Original’s whole life, and any number of editors within the profile’s limit. The author’s DID is the Original’s controller [S25], and its own history, including any pre-rotation or, for did:btco, custody of its sat, protects its keys; pre-rotation does not apply to the asset log. VH-Log recommends pre-rotation for a log with an authoritative source [S20], so that the active keys alone cannot get an entry accepted. On Bitcoin that protection comes from the sat: an entry is accepted only if inscribed on the anchoring sat (P9.12). There is no per-Original keypair; one author key can sign for all of the author’s Originals. Naming the author DID in an entry grants no authority by itself; the key must also meet P5.3.

An Original that several people govern together is a set Original instead: its signer set, of up to 32 member DIDs, and a threshold take the single author’s place (P5.19). Every member signs the genesis entry. After that, an author entry needs the threshold of the previous entry’s set, and anyone it adds must sign it too (P5.20). Each member signs with a key of its own DID, which it rotates in its own DID, and each signature is a separate proof in the entry (P5.22). So no member can act alone unless the threshold is 1, and the set keeps working while at least its threshold of members still hold their keys. An Original with one author can become a set Original by an author entry that the author and every new member sign (P5.21), but a set Original never goes back. A set is not an editor: editors, direct or inherited, still sign alone, within their grants.

### Editors

The author grants each editor permission to change named content: the name, the metadata or the resource. An editor signs its own entries with its own DID, and the author does not countersign them, so two editors can each make permitted changes while the author is offline. Every entry still names the author, and an editor entry also names the editor who made it.

An editor cannot change grants, so it cannot widen its own; it cannot add or change aliases, so it cannot publish to a new host or anchor; it cannot deactivate; and it holds none of the author DID’s keys. A grant names an editor DID, not keys, so the editor rotates its own keys in its own DID, and the author revokes the grant by an author entry. A fresh reader needs the asset log, which carries every grant and revocation, plus the history of the author DID, or of every member of a signer set, and of each editor DID that signed an entry (P7.1).

A grant can also come from a parent Original. A child Original that names a parent inherits the grants in the parent’s state at the version each of its entries pins, so an editor granted once in, say, a repository can edit every branch that names it, and a revocation in the parent reaches the branches as they pin later versions (P5.24–P5.27). Inheriting grants is the only authority a parent has: its author or signer set cannot sign the child’s author entries. A grant’s scope narrows a resource grant to some paths, or to some operations on items, and a verifier that cannot check the scope reports the change unchecked, never allowed (P5.28, P5.29).

::: example Harbor at dawn, edited by two editors
Alice grants Bob `resource: true` and Carol `metadata: true`. Bob signs an entry replacing the photo, naming Alice as author and himself as editor. Carol, on the next head, signs an entry correcting the caption metadata. Neither entry is countersigned by Alice. An entry by Bob that renames the Original, or by Carol that changes the photo, is rejected. Later Alice signs an author entry removing Bob’s grant; Bob’s entries after it are rejected, and his earlier ones stay valid.
:::

### Key rotation and compromise

To rotate, the author updates their DID: they add the new key under assertionMethod and, if the old key is compromised, remove it in the same update. Nothing is appended to the asset logs.

For an unanchored Original, an entry signed with a removed key is never reported as current (P7.9), but nothing orders it: a thief holding the key before its removal can create a branch, which stays a reported fork until the Original is anchored (P6.6, P9.16).

For an anchored Original, Bitcoin readers check each inscribed entry against the author’s DID as it stood at the entry’s inscription time (P9.15). Removing a key refuses it for entries inscribed after the removal; entries already inscribed stay current, so rotating keys after selling an Original does not invalidate it.

These limits remain:

- Before the author removes the stolen key, the thief can edit or deactivate any Original the author controls; deactivation is permanent.
- A verifier that holds only stale author DID history does not see the removal (P7.8).
- For an unanchored Original, an entry signed with a removed key can name an older author DID version and cannot be distinguished from earlier entries. Verifiers report it as historically authorized with unproven ordering, never as current (P7.9).
- A lost key can be replaced by updating the author DID, as long as the author still controls the DID; recovering a lost DID is a separate decision (section 8).

Loading evidence does not restore signing authority, and claimed timestamps cannot establish signing before revocation.
